# 路线图

CacheWitness 采用关卡式开发：每个阶段以一个可度量的关卡结束，每到一个关卡都会重新审视计划。

| 版本 | 重点 | 状态 |
|---|---|---|
| **0.1** | verify 模式：场景、三个模式、Node 钩子、CI 报告 | 已完成，待发布 |
| 0.2 | 修复方案：为每种模式提供有文档、经过验证的修复（带重新读取的租约、带版本标记的失效、代号检查）；向缓存库和 ORM 维护者提出建议 | 下一步 |
| 0.3 | check 模式（辅助）：无需修改代码，通过观察 Redis 和 PostgreSQL WAL 确认陈旧缓存状态；用观测到的事件顺序解释失败的轮次；压缩值的解码器 | 计划中 |
| 1.0 | Python 钩子、GitHub Action、按框架划分的场景指南、兼容性矩阵 | 计划中 |

视反馈而定、正在考虑的方向：

- **交错探索**：自动运行多个同步点之间的所有顺序，用户只需选择模式，由工具搜索顺序。
- 针对缓存库（keyv、cache-manager）的**自动钩子**：包装 `set`，在常见场景下无需修改应用代码。
- **钩子版本诊断**：钩子记录自己的协议版本，执行器解释由过期钩子导致的 `NOT_REACHED`。
- 不参与判定的**预热轮次**，把冷启动排除在结果之外。
- 预编译二进制；MySQL；副本延迟回填以及列表/聚合缓存模式。

包含关卡和被否决方案的详细计划见 [`docs/PLAN.md`](https://github.com/AsyncNomad/CacheWitness/blob/main/docs/PLAN.md)（韩文）。
