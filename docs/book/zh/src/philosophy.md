# 设计理念

## 1. 控制顺序，而不是抽样

概率性的压力测试问的是*"多常失败？"*，答案每次运行都不同：在我们的测量中，同样的负载（突发写入，回填放慢到 50ms）一次给出 6.5%，另一次给出 0.17%。强制交错的测试问的是*"在这个顺序下会失败吗？"*，答案每次都一样。只有后者能在 CI 中守住一个修复。

## 2. 每一轮都证明自己测到了东西

如果应被暂停的请求没有到达钩子，竞态就没有发生，通过也毫无意义。因此每一轮都会确认每个已启用的同步点确实被到达，并且在场景放行时被暂停的调用仍在等待。没有通过这项*操纵检查*的轮次报告为 `NOT_REACHED`，绝不计为通过。退出码也会区分"有轮次失败"（`1`）和"测试什么也没测到"（`2`）。

## 3. 以客户端看到的为准

判定会把应用返回的值（或缓存项）与数据库已提交的值比较，然后检查缓存能否**重新回填**。第二项检查很重要：彻底停用缓存的"修复"同样能避免陈旧值；还有一种情况是 Redis 看起来没问题，但进程内的 memoizer 仍在返回旧值。这两种情况都是这样发现的。

## 4. 把语义说清楚，包括时间

短暂陈旧的值算不算缺陷，由你的服务决定。默认判定是严格的：竞态之后立即不得有陈旧值。设置 `within_ms` 则变为有上限的判定：陈旧值必须在该时间内消失。确定性只在场景所控制的顺序和时间内成立，因此测试依赖定时器的代码的场景需要固定相关的时长。

## 5. 应用中只留很小的痕迹

钩子只是一个没有依赖的函数调用，未启用时不做任何 I/O，只使用基于 Redis 列表的小协议。应用只要能访问同一个 Redis，可以用任何语言、跑在任何主机上；其余的一切（请求、顺序、判定）都在场景和执行器中。

## 6. 可扩展的核心

步骤类型、检查和模式都是注册表。内置模式会展开为普通步骤，所以模式做的事情没有任何隐藏，新的模式或检查无需修改执行器即可接入。

## 为什么选择 Rust

- **与应用语言无关的单个二进制。** 执行器无需 Node 或 Python 运行时即可放入任何 CI 镜像，钩子则是各语言的小型库。
- **坦白说，执行器本身用任何语言都能写**：它主要是发送请求并在 Redis 上等待。Rust 的价值在于计划中的观测引擎（Redis 协议代理、PostgreSQL 逻辑复制读取器），它需要可预测的延迟和内存上限，并且要解析不可信的流量。
