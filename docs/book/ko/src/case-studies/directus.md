# 사례 연구: Directus

[Directus](https://github.com/directus/directus)는 REST와 GraphQL API를 제공하는 데이터 플랫폼입니다(Express, knex). `CACHE_ENABLED=true`, `CACHE_STORE=redis`, `CACHE_AUTO_PURGE=true`이면 GET 응답 전체를 Redis에 캐시하고, 쓰기마다 캐시 네임스페이스를 비웁니다. 캐시 구조가 Twenty와 모든 계층에서 달라 두 번째 대상으로 적합합니다.

| | Twenty | Directus |
|---|---|---|
| 프레임워크 / ORM | NestJS / TypeORM | Express / knex |
| 캐시 단위 | 엔티티 | HTTP 응답 본문 |
| 키 | `…:workspace:<id>:data` | 버전, 사용자, 경로, 쿼리의 해시 |
| 값 | JSON | 압축됨 |
| 무효화 | 키 하나 삭제 | 네임스페이스 전체 퍼지 |
| 프로세스 안 캐시 | 로컬 캐시 + 메모이저 | 없음 |

버전: v12.5.0 (`4f77933b`), Redis를 공유하는 API 인스턴스 두 개. 모든 실행은 로컬, 네트워크 격리. 실험 파일: [`lab/directus/`](https://github.com/AsyncNomad/CacheWitness/tree/main/lab/directus).

## 훅

| 지점 | 위치 | 줄 수 |
|---|---|---|
| `refill:after-read` | `middleware/respond.ts`, `setCacheValue` 앞, 키 `req.baseUrl + req.path` | 3 |
| `invalidate:before` | `cache.ts`의 데이터 캐시 퍼지 | 2 |
| `write:before-commit` | `ItemsService.updateMany`의 트랜잭션 끝 | 2 |

키는 해시이고 값은 압축돼 있으므로 시나리오는 애플리케이션을 거쳐 판정합니다. `state.app_view`가 `GET /items/articles/1`의 `/data/title`을 읽고, `X-Cache-Status`(`CACHE_STATUS_HEADER`)로 적중과 DB 읽기를 구분합니다.

## 결과 (각 20회, 모든 회차가 동기화 지점에 도달)

### stale-set

| 수정 | 결과 |
|---|---|
| 없음 | FAIL 20/20: 옛 제목을 캐시 적중으로 응답 |
| 지연된 두 번째 퍼지 (500ms), 리더 1초 붙잡음 | FAIL 20/20 |
| 세대 번호 확인 (퍼지 전에 카운터를 올리고, 옛 세대에서 시작한 재충전을 버림) | PASS 20/20 |

대조 실험: 리더를 바로 풀어 주면 지연된 두 번째 퍼지는 **10/10 통과**했습니다. 리더가 지연보다 느릴 때만 실패하는데, 평범한 테스트는 바로 그 경우를 만들지 않습니다. 인스턴스를 둘이 아니라 하나로 했을 때: 수정 없음 FAIL 10/10, 세대 번호 확인 PASS 10/10.

### failed-invalidation

| 수정 | 엄격 | 3초 안 |
|---|---|---|
| 없음 (TTL 5분) | FAIL 20/20 | FAIL 20/20 |
| 짧은 TTL (2초) | FAIL 20/20 | PASS 20/20 |
| 퍼지 재시도 | PASS 20/20 | PASS 20/20 |

수정이 없으면 쓰기는 커밋된 뒤 500을 돌려줍니다. 클라이언트는 실패로 보지만 DB에는 새 값이 있고, 캐시는 옛 값을 유지합니다.

### invalidate-before-commit

| 구성 (`hold_ms: 1000`) | 결과 |
|---|---|
| 원본 Directus (커밋 뒤 퍼지) | PASS 20/20 |
| 퍼지를 트랜잭션 안으로 옮김 (실험용 버그) | FAIL 20/20 |
| 거기에 지연된 두 번째 퍼지 추가 | FAIL 20/20 |

원본은 통과합니다. 패턴이 올바른 코드를 오탐하지 않습니다.

## 강제하지 않으면 얼마나 자주?

인스턴스 두 개, 양쪽에 리더, 라이터 하나, 훅과 수정 없음. 쓰기(또는 연달은 쓰기 묶음)마다 300ms 뒤 확인 읽기. 조건마다 독립 실행 두 번:

| 쓰기 | 인스턴스당 리더 | 실행 1 | 실행 2 |
|---|---|---|---|
| 0.5초 간격 | 2 또는 8 | 0/300, 0/300 | 0/300, 0/300 |
| 2번 연달아 | 2 | 5.0% | 2.0% |
| 2번 연달아 | 8 | 0.5% | 0% |
| 5번 연달아 | 2 | 6.0% | 2.5% |
| 5번 연달아 | 8 | 1.0% | 0.5% |

이 경쟁은 쓰기가 도착할 때 진행 중인 재충전이 있어야 하므로, 연달아 저장할 때만 나타납니다. 그러면 직전 값이 다음 쓰기나 `CACHE_TTL`까지 캐시 적중으로 남을 수 있습니다.

## 배운 것

- **번들러가 옛 훅을 굳혀 둘 수 있습니다.** Directus의 빌드가 훅을 결과물에 복사했습니다. 프로토콜이 바뀐 뒤 모든 회차가 `NOT_REACHED`였고, Redis `MONITOR`에 옛 스크립트가 보였습니다. `cawit-hook`을 외부 의존성으로 지정해 고쳤습니다.
- **라우터 기준 경로.** 첫 실행이 `NOT_REACHED`였던 이유는 마운트된 라우터 안의 `req.path`에 마운트 접두사가 없었기 때문입니다. 조작 확인 덕분에 조용한 설정 오류가 눈에 보였습니다.
- **공유 대기 연결이 인스턴스 하나짜리 시나리오를 망가뜨렸습니다.** 초기 훅은 공유 연결에서 기다렸고, 같은 프로세스의 두 번째 요청이 붙잡힌 요청 뒤에서 붙잡기가 시간 초과될 때까지 줄을 섰습니다. 회차는 순서가 깨진 채 통과했습니다. 이제 붙잡기는 자기 연결에서 기다리고, 실행기는 붙잡기가 시간 초과된 회차를 버립니다.
- **타이머에는 고정된 시간이 필요합니다.** `hold_ms` 없이는 지연 퍼지 수정이 20회 중 한 번, 콜드 스타트인 첫 회차에서 뒤집혔습니다. [경쟁 패턴](../guide/patterns.md#시간-매개변수)을 보십시오.
