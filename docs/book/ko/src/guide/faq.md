# 자주 묻는 질문

### failpoint(RocksDB SyncPoint, fail-rs, Go failpoint)와 무엇이 다른가요?

그 도구들은 한 프로세스 안, 그 프로세스의 테스트에 컴파일된 이름 붙은 지점에서 코드를 멈추거나 실패시킵니다. CacheWitness도 같은 생각에서 출발하지만, **Redis를 통해 프로세스와 서버를 넘나들며** 조율하고, **실행 중인 애플리케이션에 대한 HTTP 요청**으로 끼어들기를 만들고, **캐시 전용 패턴과 판정**(낡은 값, 재충전, 엄격·상한 판정)을 제공합니다.

### Lincheck, Fray, Coyote와는 무엇이 다른가요?

그 도구들은 JVM이나 .NET 런타임 하나 안에서 스레드 끼어들기를 탐색합니다. CacheWitness는 실제 DB와 Redis를 붙인 요청 수준에서 동작하고, 모든 끼어들기를 찾는 대신 패턴마다 하나를 강제합니다.

### 제가 모르는 경쟁도 찾아 주나요?

아니요. 패턴과 훅 위치는 사용자가 정합니다. 대신 의심하는 경쟁에 대한 결정적인 테스트와, 진짜 수정과 그럴듯한 수정을 구분하는 방법을 줍니다. 여러 훅 지점 사이의 순서를 자동으로 탐색하는 기능은 [로드맵](../project/roadmap.md)에 있습니다.

### 운영 환경에서 경쟁이 얼마나 자주 일어나는지 알 수 있나요?

아니요. 합성 부하에서 잰 비율은 같은 조건의 실행끼리도 크게 달랐고(측정에서 2.5배부터 약 38배까지), 운영 환경에 대해 말해 주는 것이 거의 없습니다. 사례 연구는 버그를 고칠 가치가 있는지 판단할 때만 이 수치를 씁니다.

### 훅을 운영 코드에 남겨 둬도 안전한가요?

그렇게 설계했습니다. `CAWIT_SYNC_URL`이 없으면 아무 일도 하기 전에 돌아오고, `NODE_ENV=production`에서는 `CAWIT_ALLOW_PRODUCTION=1`이 아닌 한 꺼져 있습니다. 그래도 테스트 계측이므로, 자체 기능 플래그나 테스트 전용 래퍼 뒤에 두는 팀도 있습니다.

### 애플리케이션 인스턴스가 꼭 두 개 필요한가요?

아니요. 붙잡힌 호출은 자기 Redis 연결에서 기다리므로 경쟁 요청을 같은 인스턴스로 보내도 됩니다. 인스턴스 둘이 운영 환경에 더 가깝습니다.

### 애플리케이션이 Node가 아닙니다.

실행기는 애플리케이션 언어를 신경 쓰지 않습니다. 그 언어의 훅이 필요하며, [프로토콜](../reference/hook-protocol.md)은 Redis 명령 몇 개입니다. Python 훅을 계획하고 있습니다.

### TLS와 비밀번호를 쓰는 관리형 Redis나 스테이징 환경에도 붙나요?

네. `rediss://`와 `AUTH`(사용자·비밀번호), `https://` 애플리케이션 URL, `sslmode`를 따르는 PostgreSQL TLS를 지원합니다. 사설 CA는 `tls.ca_file`(실행기)과 `NODE_EXTRA_CA_CERTS`(훅)로, 비밀번호는 환경 변수(`${env.X}`)로 넘길 수 있습니다. [시나리오 형식](../reference/scenario-format.md#tls와-인증)을 보십시오.

### MySQL, Redis Cluster, Memcached, Valkey에서도 되나요?

- **Valkey**: 됩니다. Redis 프로토콜을 씁니다.
- **MySQL**: 아직 안 됩니다. 판정이 PostgreSQL에서 커밋된 값을 읽습니다. 지원을 계획하고 있습니다.
- **Redis Cluster**: 아직 안 됩니다. 실행기와 훅은 프로토콜에 Redis 연결 하나와 단일 노드 키 공간을 씁니다. `cache_key` 판정에 클러스터가 필요 없다면(`app_view`를 쓰면) 캐시가 클러스터여도 프로토콜용 Redis를 별도 단일 노드로 둘 수 있습니다.
- **Memcached**: 프로토콜에는 Redis가 필요하지만, `app_view`로 판정하면 캐시는 무엇이든 됩니다.

### 훅 대신 캐시 명령을 늦추는 프록시를 쓰면 안 되나요?

측정해 봤습니다. 연결 수준 프록시에서 명령을 늦추면 head-of-line 대기열이 생겨, 실제 느린 재충전보다 경쟁 비율을 10~40배 부풀렸고, 애플리케이션의 정확한 지점에서 멈출 수도 없습니다. [프로젝트 실험 기록](https://github.com/AsyncNomad/CacheWitness/blob/main/docs/design/experiments-summary.md)을 보십시오.

### 실패가 없는데 왜 결과가 `0`이 아니라 `2`인가요?

일부 회차가 아무것도 시험하지 않았기 때문입니다. 리팩터링, 번들러 변경, 설정 변경 뒤 조용히 동기화 지점에 닿지 않게 된 테스트가 초록색으로 보여서는 안 됩니다.
