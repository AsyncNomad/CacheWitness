# 설계 철학

## 1. 순서를 표본으로 뽑지 말고 통제한다

확률적 스트레스 테스트는 *"얼마나 자주 실패하나?"*를 묻고, 그 답은 실행마다 바뀝니다. 측정해 보니 같은 부하(쓰기 몰아치기, 재충전을 50ms로 늦춤)가 한 실행에서는 6.5%, 다른 실행에서는 0.17%를 냈습니다. 순서를 강제하는 테스트는 *"이 순서에서 실패하나?"*를 묻고, 답은 매번 같습니다. CI에서 수정을 지켜 줄 수 있는 것은 두 번째 종류의 테스트뿐입니다.

## 2. 매 회차가 무언가를 시험했음을 증명한다

멈춰야 할 요청이 훅에 닿지 않았다면 경쟁은 일어나지 않았고, 통과는 의미가 없습니다. 그래서 매 회차 장전한 동기화 지점에 실제로 도달했는지, 그리고 해제할 때 붙잡힌 호출이 아직 붙잡혀 있었는지를 확인합니다. 이 *조작 확인*을 통과하지 못한 회차는 `NOT_REACHED`로 보고하고 절대 통과로 세지 않습니다. 종료 코드도 "회차가 실패함"(`1`)과 "테스트가 아무것도 시험하지 않음"(`2`)을 구분합니다.

## 3. 클라이언트가 보는 것으로 판정한다

판정은 애플리케이션이 응답하는 값(또는 캐시 항목)을 DB가 커밋한 값과 비교하고, 이어서 캐시가 **다시 채워지는지** 확인합니다. 두 번째 확인이 중요합니다. 캐시를 아예 끄는 "수정"도 낡은 값을 막고, Redis는 멀쩡해 보이는데 프로세스 안 메모이저가 옛 값을 계속 응답하는 경우도 있습니다. 둘 다 이 확인으로 찾았습니다.

## 4. 의미를, 시간까지 명시한다

잠깐 낡은 값이 버그인지는 서비스가 정합니다. 기본 판정은 엄격합니다. 경쟁 직후 낡은 값이 없어야 합니다. `within_ms`를 주면 상한 판정이 됩니다. 그 시간 안에 낡은 값이 사라지면 됩니다. 결정성은 시나리오가 통제하는 순서와 시간 안에서만 성립하므로, 타이머에 기대는 코드를 시험하는 시나리오는 관련 시간을 고정합니다.

## 5. 애플리케이션에는 작은 흔적만

훅은 의존성 없는 함수 호출 하나이고, 켜지 않으면 I/O를 하지 않으며, Redis 리스트 위의 작은 프로토콜만 씁니다. 애플리케이션은 같은 Redis에 닿기만 하면 어떤 언어로, 어떤 호스트에서 돌아도 됩니다. 나머지(요청, 순서, 판정)는 모두 시나리오와 실행기에 있습니다.

## 6. 확장 가능한 코어

단계 종류, 판정, 패턴은 레지스트리입니다. 내장 패턴은 보통 단계로 펼쳐지므로 패턴이 하는 일은 숨겨져 있지 않고, 새 패턴이나 판정은 실행기를 고치지 않고 추가됩니다.

## 왜 Rust인가

- **앱 언어와 무관한 단일 바이너리.** 실행기는 Node나 Python 런타임 없이 어느 CI 이미지에도 들어가고, 훅만 언어별 작은 라이브러리로 둡니다.
- **솔직히 실행기 자체는 어떤 언어로도 됩니다.** 대부분 요청을 보내고 Redis에서 기다리는 일입니다. Rust가 값을 하는 곳은 계획된 관측 엔진(Redis 프로토콜 프록시, PostgreSQL 논리 복제 리더)으로, 예측 가능한 지연과 메모리 상한이 필요하고 신뢰할 수 없는 트래픽을 파싱합니다.
