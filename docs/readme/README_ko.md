# CacheWitness

**캐시 동시성 버그를 원할 때 재현하고, 수정이 정말 고쳤는지 증명하는 도구**

**캐시 위트니스**

</div>

---

## 소개 (Introduction)

   **CacheWitness**(CLI: `cawit`)는 PostgreSQL + Redis 애플리케이션을 위한 Rust 오픈소스 테스트 도구입니다. **캐시 경쟁을 매번 똑같은 순서로 일으키고, 수정이 그 경쟁을 정말 막는지 CI에서 증명합니다.** 한 줄로 말하면 **"캐시 경쟁을 매번 같은 순서로 일으키고, 수정이 그 경쟁을 정말 막는지 증명하는 도구"**입니다.

   DB 앞에 Redis를 두는 cache-aside 구조는 웹 백엔드의 기본값이고, 그 경쟁은 잘 알려져 있습니다. 리더가 옛 행을 읽고, 라이터가 커밋하고 캐시를 지우고, 리더가 옛 행을 다시 써넣는 식입니다. 문제는 이런 경쟁이 **타이밍 사고**라는 점입니다. 테스트에서는 거의 나타나지 않고, 로그를 붙이면 사라지며, **일어날지 말지 모르는 사고를 상대로는 수정을 테스트할 수 없습니다.** 실제 앱에서 이를 직접 측정했습니다. 같은 부하에서 한 실행은 쓰기 몰아치기의 6.5%에서, 다른 실행은 0.17%에서 낡은 값이 남았습니다.

   **CacheWitness는 이 문제를, 순서를 기다리는 대신 통제함으로써 해결합니다.** 캐시 재충전 경로에 거는 작은 동기화 훅이 리더를 DB 읽기 직후에 멈춥니다. 시나리오 실행기는 그사이 다른 요청으로 커밋과 무효화를 마친 뒤 리더를 풀어 주고, Redis와 DB를 대조합니다. 경쟁이 매번 일어나므로 테스트는 수정 전에는 매번 실패하고 수정 후에는 매번 통과합니다. CacheWitness는 다음과 같은 명확한 철학을 바탕으로 설계되었습니다. **“경쟁을 기다리지 않는다. 일으키고, 수정을 증명한다.”**

   대상은 **캐시 라이브러리·ORM 개발자, 그리고 캐시 코드를 직접 짜는 팀**입니다. 흔들리지 않는 캐시 무효화 회귀 테스트가 필요한 경우에 씁니다.

## 해결하는 문제 (The Problem)

| 경쟁 | 무슨 일이 생기나 | 흔하지만 부족한 "수정" |
|---|---|---|
| stale-set 경쟁 | 리더가 옛 값을 읽음 → 라이터가 커밋·DEL → 리더가 옛 값을 SET | SET 전에 버전 비교: DEL 뒤에는 비교할 값이 없다 |
| 커밋 전 무효화 | 트랜잭션 안에서 DEL → 커밋 전에 다른 요청이 옛 값으로 재충전 | 지연 이중 삭제: 창을 좁힐 뿐 닫지 못한다 |
| 무효화 실패 | DEL이 네트워크·권한 문제로 실패하고 재시도 없음 | 짧은 TTL: 피해를 줄일 뿐 고치지 못한다 |
| 레플리카 지연 재충전 | DEL 뒤 지연된 레플리카가 옛 값을 줌 | 미스 때 primary에서 읽기: 모든 재충전 경로가 그래야 한다 |

안전한 패턴(리스, 버전이 남는 무효화)은 알려져 있고, **그 함정도 알려져 있습니다.** 실제 앱에서 한 첫 실험에서도 그럴듯한 수정 두 개가 맞아 보였지만 틀렸습니다. 버전 비교 SET은 아무 효과가 없었고, 다시 읽기 없는 리스는 프로세스 안의 메모이저가 옛 값을 10초 동안 응답하게 만들었습니다. 경쟁을 강제하는 테스트만 이 차이를 보여줍니다.

## 빠른 시작 (Quick Start)

> v0.1은 아직 배포 전입니다. 그때까지는 `cargo build --release`로 실행기를 빌드하고 [`hooks/node`](../../hooks/node)의 훅을 씁니다. 실제 앱에 대한 동작 예: [`lab/twenty/`](../../lab/twenty/) (Twenty CRM), [`lab/directus/`](../../lab/directus/) (Directus).

### 1. 설치

```bash
cargo install cawit                 # 실행기, 단일 바이너리
npm install --save-dev cawit-hook   # 훅, 의존성 없음
```

### 2. 재충전 경로에 동기화 훅 걸기

DB를 읽은 직후, 캐시에 쓰기 전에 호출 하나를 넣습니다. `CAWIT_SYNC_URL`이 있고 테스트가 장전할 때만 동작합니다(`NODE_ENV=production`이면 `CAWIT_ALLOW_PRODUCTION=1` 없이는 꺼짐).

```ts
import * as cawit from "cawit-hook";

const row = await db.findOne(id);
await cawit.syncPoint("refill:after-read", key);
await cache.set(key, serialize(row));
```

### 3. 경쟁을 적고 실행하기

```yaml
# stale-set.yaml
name: stale-set
runs: 20
apps: { a: "http://127.0.0.1:3000", b: "http://127.0.0.1:3001" }
redis: redis://127.0.0.1:6379
postgres: "host=127.0.0.1 user=postgres password=postgres dbname=app"
requests:
  update: { method: PATCH, path: /articles/1, json: { title: "${value}" } }
  read:   { method: GET,   path: /articles/1 }
state:
  db_query: "select title from articles where id = 1"
  app_view: { app: a, request: read, field: /title, hit_header: x-cache }
pattern:
  stale-set: { reader: a, writer: b, write: update, read: read, key: /articles/1 }
```

```bash
# 앱을 CAWIT_SYNC_URL=redis://127.0.0.1:6379 로 띄운 뒤
cawit verify stale-set.yaml --junit report.xml   # 한 번이라도 낡은 값이 남으면 종료 코드 1
cawit verify stale-set.yaml --show-steps          # 패턴이 하는 일 보기
```

각 회차는 다음 순서로 진행됩니다.

1. 서버 A로 쓴다 (커밋하고 무효화).
2. 훅을 장전하고 A로 읽는다. A는 미스로 DB를 읽고 훅에서 멈춘다.
3. 서버 B로 더 새 값을 쓴다 (커밋하고 무효화).
4. A를 풀어 준다. A는 읽어 둔 값을 쓴다.
5. 리더가 DB에 커밋된 값을 받는지 확인한다.
6. 캐시가 최신 값으로 다시 채워지는지 확인한다 (수정이 캐시를 아예 막으면 안 된다).

훅에 도달하지 않았거나 붙잡기가 시간 초과로 풀린 회차는 통과로 세지 않고 버립니다. 패턴, 단계, 판정: [`docs/scenarios.md`](../scenarios.md) (영어).

### 4. 결과 확인

```
stale-set (20회, 모든 회차가 훅에 도달)
  수정 전                        낡은 값 20/20                 FAIL
  버전 비교 SET                  낡은 값 20/20                 FAIL  DEL 뒤에는 비교할 값이 없음
  리스                           낡은 값  0/20, 재충전  0/20   FAIL  메모리에서 옛 값을 응답
  리스 + 거부 시 다시 읽기       낡은 값  0/20, 재충전 20/20   PASS
```

## 설계 철학 (Design Philosophy)

### 1. 순서를 표본으로 뽑지 말고 통제한다

확률적 스트레스 테스트는 "얼마나 자주 실패하나?"를 묻고, 그 답은 실행마다 바뀝니다. 순서를 강제하는 테스트는 "이 순서에서 실패하나?"를 묻고, 답은 매번 같습니다. 그래서 CI 회귀 테스트로 쓸 수 있습니다.

### 2. 매 회차가 무언가를 시험했음을 증명한다

훅에 도달하지 않았다면 경쟁은 일어나지 않았고, 통과는 아무 의미가 없습니다. 매 회차 훅 도달 여부를 기록하고, 도달하지 않은 회차는 버립니다(조작 확인).

### 3. 판정은 상태로, 설명은 순서로

판정은 단순합니다. Redis가 DB에 커밋된 값을 들고 있는가, 그리고 그 뒤 캐시가 다시 채워지는가. 실패했을 때는 관측된 사건의 순서(Redis 실행 순서와 PostgreSQL 커밋 순서)로 경위를 설명할 계획입니다. 벽시계 타임스탬프는 측정에서 믿을 수 없다는 것이 드러났기 때문입니다.

### 4. 왜 Rust인가

- **앱 언어와 무관한 단일 바이너리:** 실행기는 Node나 Python 런타임 없이 어느 CI 러너에도 들어가고, 훅만 언어별 작은 라이브러리로 둡니다.
- **솔직히 실행기 자체는 어떤 언어로도 됩니다:** 대부분 요청을 보내고 Redis에서 기다리는 일입니다. Rust가 값을 하는 곳은 계획된 관측 엔진(Redis 프로토콜 프록시, PostgreSQL 논리 복제 리더)으로, 예측 가능한 지연과 메모리 상한이 필요하고 신뢰할 수 없는 트래픽을 파싱합니다.

## 주요 기능 (Key Features)

- **🎯 결정적 재현:** 알려진 캐시 경쟁 패턴을 매번 같은 순서로 일으킴
- **✅ 수정 검증:** 수정 전 실패, 수정 후 통과, 그리고 캐시가 다시 채워지는지까지 확인
- **🧪 내장 패턴:** stale-set, 무효화 실패(장애 주입), 커밋 전 무효화. 레플리카 지연 재충전은 계획
- **🔍 조작 확인:** 훅에 도달하지 않은 회차는 버림
- **🧾 순서 기반 설명 (계획):** 실패한 회차에 커밋·삭제·쓰기의 관측 순서를 함께 제공. 지금은 실패 회차에 리더가 받은 값과 DB 값을 보여줌
- **👀 보조 기능, check 모드 (앱 코드 무수정):** Redis와 PostgreSQL WAL을 관찰해 낡은 캐시 상태를 사실로 확정

## 측정한 것 (What We Measured)

모든 실험은 로컬에서, 앱 실험 환경을 네트워크와 격리한 상태로 돌렸습니다. 자세한 내용: [`docs/design/experiments-summary.md`](../design/experiments-summary.md).

- **Twenty CRM에서 순서를 강제 (각 20회):** 수정 전 20/20 낡음, 버전 비교 SET 20/20 낡음, 리스 0/20 낡음이지만 재충전 안 됨(프로세스 안 메모이저), 리스 + 다시 읽기 0/20 낡음·20/20 재충전.
- **Directus에서 순서를 강제 (각 20회):** 수정 전 20/20 낡음, 지연 이중 삭제는 리더가 지연보다 느리면 20/20 낡음(빠른 리더에서는 10/10 통과하므로 보통 테스트를 빠져나감), 세대 번호 확인 20/20 통과.
- **순서 대신 확률로 재면:** 같은 몰아치기 부하에서 한 실행은 6.5%, 다른 실행은 0.17%에서 낡은 값이 남았습니다. 프록시로 캐시 쓰기를 늦추면 실제 느린 재충전보다 최대 10~30배 부풀려졌습니다.
- **실제 테스트 스위트에서의 탐지:** 캐시된 행 변경 1,528건 중 1,527건이 무효화됐습니다(중앙값 1.7ms). 정답 실험에서 낡은 상태는 빠짐없이 확정했지만(157/157), 결정적인 무효화 버그는 드물었습니다.

이 결과 때문에 CacheWitness는 강제 재현과 수정 검증에 집중합니다.

## 기존 도구와의 관계 (Related Tools)

지정한 지점에서 코드를 멈춰 순서를 강제하는 기법 자체는 새롭지 않습니다. CacheWitness가 다른 점은 지점이 놓이는 곳과 판정하는 대상입니다.

| 도구 | 하는 일 | 차이 |
|---|---|---|
| RocksDB SyncPoint, fail-rs (TiKV), failpoint (Go) | 한 프로세스 안에 컴파일된 동기화·장애 지점 | CacheWitness는 Redis를 통해 프로세스·서버를 넘나들며, HTTP 요청으로 시나리오를 움직입니다 |
| Lincheck, Fray (JVM), Coyote (.NET) | 한 런타임 안의 스레드 끼어들기 탐색 | CacheWitness는 실제 DB와 Redis를 붙인 요청 단위로 동작합니다 |
| Jepsen | 장애 상황에서 분산 DB의 일관성을 블랙박스로 시험 | CacheWitness는 앱의 캐시 로직이 대상이고, 캐시 전용 패턴과 판정을 둡니다 |

## 범위 (Scope)

| 항목 | 첫 공개 버전 (v0.x) | 이후 |
|---|---|---|
| 훅 | Node/TS | Python, 그 밖의 언어 |
| 시나리오 | stale-set, 커밋 전 무효화, 무효화 실패 | 레플리카 지연 재충전, 목록·집계 캐시 |
| DB / 캐시 | PostgreSQL, Redis/Valkey 단일 노드 | MySQL, Redis Cluster |
| check 모드 (보조) | verify 엔진 이후 | — |

**CacheWitness가 하지 않는 것:**

- 알려 주지 않은 경쟁을 찾아내지 않습니다. verify는 알려진 순서에 대한 회귀 테스트입니다.
- 운영 환경에서 경쟁이 얼마나 자주 일어나는지 추정하지 않습니다.
- 캐시를 고치거나 대체하지 않습니다.
