0단계와 1단계에서 한 실험을 한곳에 모은 문서다. 수치의 출처와 자세한 해석은 각 결과 문서에 있다.

- 0단계(프로토타입 판정의 정확도): [`phase0-results.md`](phase0-results.md)
- 1단계(실제 앱 적합성, Twenty race 실험): [`phase1-results.md`](phase1-results.md)

모든 실험은 로컬 WSL2에서만 돌렸다. Twenty 실험은 외부 경로가 없는 docker 내부 네트워크 안에서 돌렸다(`lab/twenty/compose.yaml`). 실행 결과는 `lab/out/`에 남고 git에는 넣지 않는다.

## 3. 측정 함정 (다시 빠지지 않도록)

| 함정 | 증상 | 대응 |
|---|---|---|
| WSL2 벽시계가 수십 초마다 약 −2.8초 이동 | 응답 지연 중앙값 2.8초, 가짜 "늦은 무효화" 17건, 가짜 옛 값 SET 9~60건 | 단조 시계로 기록하고 벽시계 표본으로 보정. 판정은 순서로 |
| 같은 호스트의 Redis와 PostgreSQL은 같은 벽시계를 읽음 | 두 시계를 비교해서는 이동을 감지할 수 없음 (실측) | 도구 자체의 단조 시계와 비교 |
| 앱 설정 파일(`.env.test`)이 환경 변수보다 우선 | 증폭기를 붙인 실행이 조용히 프록시를 우회 | **조작 확인**: 지연 적용 횟수 = 대상 쓰기 수가 아니면 실행 실패 |
| `bash -c` 안의 `\|` | jest 출력이 파이프로 새어 EPIPE | `printf %q` |
| 분석기의 0.0 처리 | 지속 시간 0ms가 "모름"으로 바뀜 | `is None`으로 비교 |
| 실행 간 변동 | 같은 조건에서 2.7배 차이 | 실행 한 번끼리 비교하지 않기. 반복 측정 |
| 작은 표본의 0건 | 일정 20ms 98회 0건을 "일정한 지연은 안전"으로 읽음. 600회로 다시 재니 남았다 | 0건이면 항상 95% 상한을 함께 보고, 결론은 상한 기준 |
| 실행 내 신뢰구간 | 실행 하나 안의 수백 회로 낸 구간이 다른 실행과 맞지 않음 (6.5% 대 0.17%) | 독립 실행 여러 번, 실행 간 퍼짐 보고 |
| 초기화의 거짓 성공 | DB 초기화는 성공인데 시드가 실패, 모든 요청이 `Workspace not found` | 초기화 뒤 시드 결과를 직접 확인 |
| 지나치게 엄격한 조작 확인 | MONITOR 시작 전 재충전 5회 때문에 정상 실행이 실패 처리됨. 실패 처리가 WAL 수집보다 먼저라 분석 불가 | WAL 먼저 수집, "지연 적용 ≥ 관측 재충전, 초과 0.5%+5 이내" |

## 4. 아직 답하지 못한 질문

- 같은 조건에서 실행마다 체제가 갈리는 이유는 무엇인가 (일정 50ms 1회차에서 관찰한 되먹임: 쓰기가 자기가 무효화하는 캐시를 인증에 씀)
- 앱 코드를 고치지 않고 위험을 정량화할 수 있는가. 후보는 DB 쪽 선택 지연인데, Twenty는 쓰기 뒤에 같은 SQL로 다시 조회하므로 효과가 줄 것으로 예측된다
- 증폭기 곡선은 왜 50ms 근처에서 정점인가
- 쓰기 출처(앱 대 테스트 픽스처)를 어떻게 구분하는가 (`%x` 로그 방식은 자동 커밋에서 실패함을 실측)
- 다른 앱에서도 같은 결과가 나오는가 (지금까지 실제 앱은 Twenty 하나)
