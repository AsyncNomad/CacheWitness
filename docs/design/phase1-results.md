# 1단계 결과 기록: 실제 앱 적합성

1단계의 목표는 가장 큰 리스크인 **실제 앱의 매핑 부담**을 싸게 확인하는 것이다 (PLAN 13장). 계획서의 통과 조건은 "오픈소스 앱 3개 중 2개 이상이 30줄 이내로 매핑되고, 테스트가 커밋하거나 커밋하도록 바꿀 수 있을 것"이다.

## 1. 코드 조사: PostgreSQL + Redis 캐시를 쓰는 오픈소스 8개 (2026-10-15)

각 저장소의 기본 브랜치를 얕게 클론해서 캐시 계층의 코드를 읽었다.

| 앱 | 언어 | 캐시 계층 | Redis에 들어가는 값 | 무엇을 캐시하나 | 키 형식 | v0(JSON)로 읽을 수 있나 |
|---|---|---|---|---|---|---|
| Twenty | TS (NestJS) | `cache-manager-redis-yet`, 자체 `CoreEntityCacheService` | JSON | **행 캐시**: user, workspace, userWorkspace (+ 버전 표시용 `:hash` 키, 부정 캐시 표식) | `[테스트 접두사:]engine:core-entity:<엔티티>:<uuid>:data` | **예** |
| n8n | TS | ioredis 기반 cache-manager | JSON | **행 캐시**: 웹훅 (`webhook:<method>-<path>`), 그 밖에 설정·토큰 | `{n8n:cache}:` 해시태그 접두사 + 키 | 예. 단 키가 복합 키(`method`, `path`)이고 구분자 `-`가 경로에도 나와 역해석이 모호. 기본 설정은 메모리 캐시이고 Redis는 큐 모드에서만 쓴다 |
| Medusa | TS | 자체 `caching-redis` 모듈 | HSET `data` 필드에 JSON, 2KB 넘으면 **gzip** | **쿼리 결과 캐시**, 태그로 무효화 | 해시된 키 | 행 매핑 불가 |
| PostHog | Python (Django) | django-redis + zstd 압축기 | **pickle(JSON 문자열)**, 크면 **zstd** | 행 캐시: team (`team_token:<api_token>`), 그 밖에 집계·쿼리 캐시 다수 (호출 지점 557곳) | `posthog:1:<키>` | 아니오 (pickle·zstd 해제가 필요). 키가 기본 키가 아니라 유일 컬럼(`api_token`). Redis 레플리카 읽기 사용 |
| Paperless-ngx | Python (Django) | Django `RedisCache` + django-cachalot | pickle | 문서 메타데이터·분류기 결과 등 파생 값, cachalot 쿼리 캐시 | `<접두사>:1:<키>` | 아니오. 행 매핑도 거의 불가 |
| Saleor | Python (Django) | `django_cache_url` | pickle | 소수 (호출 지점 28곳) | `:1:<키>` | 아니오 |
| Mastodon | Ruby (Rails 8.1) | `redis_cache_store` | Rails 캐시 형식(Marshal 기반) | 목록·파생 값 대부분 (차단 ID 목록, 필터, 추천) | 자유 형식 | 아니오 |
| Discourse | Ruby | 자체 `Cache` 클래스 | Ruby 직렬화 | 목록·파생 값 | 네임스페이스 접두사 | 아니오 |

**관찰**

- **JSON을 쓰는 앱은 Node 계열뿐이다.** Django 계열은 pickle, Rails 계열은 Marshal이 기본이다. PLAN 9.3의 우려가 그대로 맞았다.
- **행 캐시는 생각보다 드물다.** 8개 중 행 단위 cache-aside가 핵심인 앱은 Twenty, n8n, PostHog(team) 정도다. 나머지는 쿼리 결과·목록·파생 값 캐시가 중심이라 "테이블 1:1 매핑"이 성립하지 않는다.
- **값이 여러 겹으로 싸여 있다.** PostHog는 JSON 문자열을 pickle하고, 크면 zstd로 압축한다. Medusa는 2KB 이상이면 gzip을 쓴다. 디코더는 하나가 아니라 **연쇄**(zstd → pickle → JSON)로 설계해야 한다.
- **키가 기본 키가 아닌 경우가 있다.** PostHog는 `api_token`(유일 컬럼), n8n은 복합 키다. 매핑에 "조회 컬럼" 개념이 필요하다.
- **접두사가 환경마다 다르다.** 테스트 전용 접두사(Twenty `integration-tests:`), 해시태그(n8n `{...}`), Django 버전 접두사(`:1:`).

## 2. Twenty를 실제로 돌려 본 결과

조사에서 v0와 가장 잘 맞는 Twenty를 골라, 통합 테스트를 실제 PostgreSQL 16과 Redis 7.2에 붙여 돌렸다.

- 환경: `lab/twenty/compose.yaml`, 기록: `lab/twenty/record.sh`, 분석: `lab/twenty/analyze.py`
- Redis는 `MONITOR`로 모든 명령을 기록했다. 프로토타입은 MGET·MSET·다중 키 DEL을 해석하지 못하므로, 이 측정에는 MONITOR가 맞다.
- PostgreSQL은 DB 초기화 뒤에 만든 test_decoding 슬롯으로 커밋을 기록했다.

### 2.1 테스트 환경의 수명주기

| 항목 | 실제 |
|---|---|
| DB 초기화 | `DROP SCHEMA ... CASCADE` 후 마이그레이션 (TRUNCATE도 DB 재생성도 아니다) |
| 테스트 데이터 | 커밋한다 (트랜잭션 롤백 방식 아님). check 모드의 전제를 만족한다 |
| 스키마 | 워크스페이스마다 스키마를 실행 중에 새로 만든다 (`workspace_<id>`) |
| 병렬성 | `maxConcurrency: 1`, `--runInBand` |
| Redis | **캐시와 BullMQ 큐가 같은 Redis를 쓴다.** 명령의 대부분이 큐 트래픽이다 |
| 키 접두사 | 테스트에서는 `integration-tests:`가 앞에 붙는다 |

**계획에 주는 의미**

- 스키마 단위 DROP은 PLAN 9.2의 "DB 재생성" 처리와 다르다. 테이블 단위 publication은 스키마가 지워지면 함께 사라지므로, attach-on-ready는 **스키마 재생성**도 감지해야 한다.
- 캐시와 큐가 같은 Redis에 있으면 keyspace 알림이 큐 트래픽까지 모두 발행된다. 구독 패턴을 매핑된 키로 좁혀도 서버의 발행 비용은 그대로다 (PLAN 17장의 비용 측정 항목).

### 2.2 v0 명령 범위와의 차이

엔티티 캐시 키에 실제로 쓰인 명령:

| 명령 | 용도 | PLAN 9.1 v0 범위 | 프로토타입 |
|---|---|---|---|
| `MGET` | `:data`와 `:hash`를 한 번에 읽기 | 포함 | **미지원** |
| `SET ... PX` | 캐시 채우기 | 포함 | 지원 |
| `DEL k1 k2` | `:data`와 `:hash`를 한 번에 무효화 | 포함 | **첫 키만 기록** |
| `EVAL` (내부에서 `SET`) | 여러 키를 TTL과 함께 원자적으로 쓰기 | 키 선언 + keyspace 알림 | **미지원** |
| `GET` | `:hash`만 읽어 로컬 캐시 검증 | 포함 | 지원 |

- **MONITOR는 Lua 스크립트 안의 명령도 `[0 lua]`로 기록한다.** 스크립트 내부 쓰기를 관측하는 또 다른 방법이다. 다만 MONITOR는 서버 성능에 영향이 커서 CI 전용이다.

### 2.3 매핑 부담

캐시된 값의 필드는 **모두 DB 컬럼 이름과 같고**, 컬럼의 부분집합이다.

| 엔티티 | 캐시 필드 | 컬럼 | 캐시에 없는 컬럼 |
|---|---|---|---|
| workspace | 39 | 40 | `deletedAt` |
| user | 11 | 13 | `deletedAt`, `passwordHash` |
| userWorkspace | 8 | 8 | — |

그래서 필드 이름 매핑 없이 엔티티마다 4~5줄로 매핑된다.

```yaml
mappings:
  - key: "{prefix}engine:core-entity:user:{id}:data"
    table: core."user"
    pk: [id]
    value: { format: json }
    soft_delete: deletedAt
  - key: "{prefix}engine:core-entity:workspace:{id}:data"
    table: core.workspace
    pk: [id]
    value: { format: json }
    soft_delete: deletedAt
  - key: "{prefix}engine:core-entity:user-workspace:{id}:data"
    table: core."userWorkspace"
    pk: [id]
    value: { format: json }
    negative: { value: "\"__CORE_ENTITY_NOT_FOUND__\"" }
# ":hash" 키는 랜덤 UUID 버전 표식이다. 행과 대응하지 않으므로 미매핑으로 둔다.
```

**약 17줄로 30줄 기준을 통과한다.** 다만 두 가지는 현재 설계에 없다.

- **소프트 삭제**: `deletedAt`은 캐시되지 않는다. 그래서 행이 소프트 삭제돼도 겹치는 필드끼리 비교하면 "최신"으로 보인다. `soft_delete` 컬럼을 tombstone으로 다루는 설정이 필요하다.
- **버전 표식 키**: `:hash`처럼 행이 아니라 캐시 자신의 버전을 나타내는 키가 있다. 미매핑으로 나열하되, "버전 표식"으로 분류하면 보고서의 미매핑 목록이 덜 시끄럽다.

### 2.4 첫 발견: 삭제된 userWorkspace가 캐시에 7일 남는다

`graphql/suites/user*` 스위트 11개를 돌린 기록에서, 엔티티 행이 캐시된 상태에서 바뀐 경우가 13건이었다. 12건은 바로 무효화됐고, **1건은 끝까지 무효화되지 않았다.**

- `core."userWorkspace"` 행이 **DELETE**됐는데, 캐시 항목 `...:user-workspace:<id>:data`가 그대로 남았다. TTL은 `PX 604800000`(7일)이다.
- 코드 확인: `UserWorkspaceService.deleteUserWorkspace`는 행을 지우지만 엔티티 캐시를 무효화하지 않는다. 호출 지점 세 곳 중 `workspace.service.ts`만 호출 뒤에 `invalidate('userWorkspaceEntity', ...)`를 부르고, **`workspace-member-delete-one.post-query.hook.ts`와 `user.service.ts`는 부르지 않는다.**
- 영향 확인: 이 캐시를 읽는 곳은 JWT 인증 전략(`resolveUserContext`) 한 곳뿐이다. 그런데 인증 전략은 그 뒤에 워크스페이스 멤버 맵을 다시 확인하고, 이 맵은 두 경로 모두에서 다시 계산된다. **따라서 제거된 멤버가 인증을 통과하지는 않는다.** 예외는 워크스페이스가 생성 중 상태일 때다(그 확인을 건너뛴다).

**분류**: 실제 캐시 불일치(삭제된 행이 최대 7일 캐시됨)이지만, 이중 확인 때문에 사용자 피해는 드러나지 않는다. 검토에서 지적한 "탐지는 됐지만 버그로 인정받기 어려운 경우"(PLAN 15장)의 실제 사례다. upstream에 보고한다면 보안 문제가 아니라 일관성 문제로, 이중 확인이 있다는 점을 함께 적어야 한다.

(Twenty 커밋 `c3ba1401`, 2026-10-14 기준)

### 2.5 전체 통합 테스트 기록

같은 방식으로 전체 통합 테스트를 돌렸다. jest 프로세스가 스위트 **432개**를 돈 뒤 8GB 힙 한도를 넘겨 종료됐으므로, 아래는 그 432개 분량이다.

| 항목 | 값 |
|---|---|
| Redis 명령 | 약 685만 건. 대부분 BullMQ 큐(`ZCARD`, `LLEN`, `LINDEX`, `EVALSHA` 66만 건). **엔티티 캐시 관련은 9,116줄(0.13%)** |
| MONITOR 기록 크기 | 18GB |
| 엔티티 행 변경 (WAL) | workspace UPDATE 1,621, user UPDATE 54, INSERT·DELETE 수십 건 |
| 캐시된 상태에서 행이 바뀐 경우 | **1,528건** |
| 그중 무효화된 경우 | 1,527건. 커밋 → 무효화 중앙값 **1.7ms**, p90 6.5ms |
| 1초 넘게 걸린 경우 | 20건. **17건은 시계 이동 때문에 생긴 가짜**(2.6), 남은 3건은 아래 표 |
| 끝까지 무효화되지 않은 경우 | 1건 (아래 표) |

| 경우 | 관측 | 판정 |
|---|---|---|
| workspace `activationStatus` → SUSPENDED, 36.5초 뒤 무효화 | 37ms 뒤 다시 ACTIVE로 돌아감 | **테스트 픽스처**가 SQL로 직접 바꾼 것(`failing-sign-up-in-non-active-workspace`). 앱을 거치지 않았고, 낡은 구간도 허용치(500ms)보다 짧다 |
| user DELETE, 무효화 없음 | 같은 트랜잭션에서 appToken·userSession도 삭제 | **테스트 픽스처**의 `DELETE FROM core."user"` (여러 스펙에 있음) |
| workspace `logoFileId` → null, 8.3초 뒤 무효화 | `updateWorkspace(logo: null)` 뮤테이션 경로. 코드는 UPDATE 직후 `invalidate`를 부르는데, 그 사이 Redis 트래픽은 초당 약 8천 건으로 계속됐다 | **판단 불가.** 앱이 늦었는지, 다른 경로의 커밋인지 프록시·WAL만으로는 가릴 수 없다. 앱 쪽 증거(요청 ID, 호출 시각)가 필요하다 |

2.4의 userWorkspace DELETE(앱 경로의 무효화 누락)는 이 실행에서는 다시 나오지 않았다. 해당 시점에 캐시돼 있지 않았거나, 그 스위트가 OOM 전에 돌지 않았기 때문이다.

### 2.6 측정 함정: Redis MONITOR의 타임스탬프도 벽시계다

처음 분석에서는 "1초 넘게 늦은 무효화"가 20건 나왔다. 그런데 MONITOR 기록은 Redis가 실행한 순서인데도 타임스탬프가 +2,632ms에서 +1.7ms로 **거꾸로** 갔다. Redis와 PostgreSQL 모두 벽시계를 쓰므로, WSL2의 약 −2.8초 이동이 두 기록에 그대로 들어간다(이 실행 중 104회 감지). 실행 순서로 다시 보면, 해당 커밋 직후 1.7ms 만에 정상적으로 무효화됐다.

분석기는 두 기록에서 시계가 거꾸로 가는 지점을 찾고, 그 근처(±3.5초)에 걸린 판정을 따로 표시하도록 고쳤다. **0단계(3.1)와 같은 교훈이 다른 형태로 다시 나왔다.** 서로 다른 프로세스의 벽시계 타임스탬프를 비교하는 순간, 이동 근처의 판정은 믿을 수 없다.

## 3. 통과 조건 판정

| 앱 (생태계) | 30줄 이내 매핑 | 테스트가 커밋하는가 | 판정 |
|---|---|---|---|
| Twenty (Node/TS) | **예** (약 17줄) | 예 | 통과. 단 아래 4장의 기능이 필요 |
| PostHog (Django) | 아니오. pickle + zstd 디코더 필요, 키가 유일 컬럼 | (실행하지 않음. ClickHouse·Kafka 등 의존성이 무겁다) | v0로는 불가 |
| Mastodon·Discourse (Rails) | 아니오. Marshal 기반 직렬화, 캐시 대부분이 목록·파생 값 | (실행하지 않음) | v0로는 불가 |

참고로 n8n(Node/TS)도 JSON이라 읽을 수 있지만, 키가 복합 키이고 Redis 캐시는 큐 모드에서만 쓴다.

**판정: 매핑 모델은 통과, 직렬화 포맷 때문에 불통과.** 계획서 13장의 분기에 따라 다음과 같이 정했다 (2026-10-15, 사용자 결정).

- **v0에 디코더 연쇄를 넣는다: gzip·zstd 압축 해제 + 기본 타입만 다루는 "단순 pickle"** (str·bytes·dict·list·tuple·int·float·bool·None). 모델 객체를 통째로 pickle한 값과 Ruby Marshal은 `UNSUPPORTED`로 보고한다. 예상 비용 약 1주.
- 디코더로 **판정까지 가능해지는 대상은 PostHog의 team 캐시**다. Medusa는 값을 읽을 수는 있지만 쿼리 결과 캐시라 행·버전을 정할 수 없으므로, 미매핑 키로 보고된다.
- 알려진 제약: PostHog 테스트는 대부분 롤백 방식이다. 기본 테스트 클래스 `BaseTest`·`APIBaseTest`가 `TestCase`이고, 이를 쓰는 파일이 약 2,680개, 커밋하는 `TransactionTestCase` 계열은 약 230개다. 그래서 check 모드로 PostHog를 볼 때는 커밋하는 테스트나 race 모드(부하)에 의존한다. Redis 레플리카 읽기는 `REDIS_READER_URL` 기본값이 `None`이라 테스트에서는 문제되지 않는다. zstd 압축은 `USE_REDIS_COMPRESSION`이 켜져 있고 512바이트를 넘을 때만 적용된다.
- 외부 검토는 "단순 pickle은 PostHog 실현 가능성을 하루 점검한 뒤 결정"을 권했다. 롤백 방식 테스트라는 제약을 알고도 넣기로 한 이유는, Python(Django) 생태계를 v0에서 통째로 잃지 않기 위해서다.

**check 모드의 수확이 적을 수 있다.** 잘 관리된 코드베이스(Twenty)에서는 캐시된 행 변경 1,528건 중 1,527건이 바로 무효화됐다. 결정적인 무효화 누락은 드물다. 프로젝트의 핵심 가설("교과서 패턴도 동시성 아래에서 낡은 값을 남긴다")은 아직 실제 앱에서 검증하지 않았으므로, 다음 작업은 Twenty에서의 race 검증이다(5장).

**OOM은 실행 방식 탓이다.** Twenty CI는 통합 테스트를 16개 샤드로 나누고 샤드마다 12GB 힙을 준다. 한 프로세스로 전체를 돌린 것이 원인이다. MONITOR는 별도 `redis-cli` 프로세스가 파일로 쓰므로 Node 힙과 무관하다.

## 4. 설계에 반영할 것

| 발견 | 반영 |
|---|---|
| 테스트 픽스처가 앱을 거치지 않고 DB를 직접 고친다 (Twenty의 여러 스펙) | **쓰기 출처 구분이 필요하다.** 그대로 두면 픽스처 쓰기가 "무효화 누락"으로 보고된다. **`log_line_prefix`의 `%x`로 WAL의 xid와 맞추는 방법은 쓸 수 없다**: 실험해 보니 자동 커밋 문장은 실행 전·후 로그 모두 `%x`가 0이었다(명시적 트랜잭션 안에서만 xid가 찍힌다). 남은 후보: 픽스처 연결에서 복제 origin 설정(`pg_replication_origin_session_setup`, superuser 필요, 미검증), `pg_logical_emit_message`로 픽스처 구간 표시(픽스처 코드 수정), 출처를 모르는 커밋을 `UNKNOWN_WRITER`로 분류. 2단계 설계에서 정한다 |
| 같은 호스트의 Redis와 PostgreSQL은 같은 벽시계를 읽는다 | **두 시계를 서로 비교해서는 시계 이동을 감지할 수 없다.** 75초 실측에서 두 시계가 함께 약 −2.95초씩 3번 이동했고, 둘의 차이는 내내 약 +70ms(측정 지연)로 일정했다. 도구 자체의 단조 시계와 비교해야 한다 (PLAN 9.5) |
| 캐시에 없는 컬럼으로 소프트 삭제한다 (`deletedAt`) | 매핑에 `soft_delete` 컬럼. 값이 생기면 tombstone으로 처리 |
| 부정 캐시 표식 값 (`"__CORE_ENTITY_NOT_FOUND__"`) | 매핑의 `negative` (PLAN 9.3에 이미 있음) |
| 행이 아니라 캐시 자신의 버전을 나타내는 키 (`:hash`) | 미매핑 중 "버전 표식"으로 분류해 보고서 소음을 줄인다 |
| 값이 여러 겹이다 (JSON → pickle → zstd, JSON → gzip) | `ValueDecoder`를 연쇄로 구성 |
| 키가 기본 키가 아니다 (유일 컬럼, 복합 키) | 매핑에 조회 컬럼(`lookup: [api_token]`) |
| 캐시와 큐가 같은 Redis를 쓴다 (명령의 99.9%가 큐) | 관측 계층은 매핑되지 않은 키를 파싱 직후 버린다. keyspace 알림 비용 측정에 큐 트래픽을 포함한다 |
| 실제 값이 크다 (워크스페이스 메타데이터 수 MB) | 값 전체를 보관하지 않고 필드 지문만 (PLAN 9.7 유지) |
| `DROP SCHEMA ... CASCADE` 초기화, 워크스페이스마다 스키마 생성 | attach-on-ready가 DB뿐 아니라 스키마 재생성도 감지 (PLAN 9.2) |
| MGET, 다중 키 DEL, EVAL 내부 SET | v0 명령 범위(PLAN 9.1)가 맞다. 프로토타입은 셋 다 처리하지 못했다 |
| MONITOR는 스크립트 내부 명령까지 실행 순서대로 보여준다 | CI 전용 보조 관측 수단으로 재검토할 가치가 있다. 응답을 볼 수 없다는 한계(PLAN 16장)는 그대로다 |

(Twenty 커밋 `c3ba1401`, 2026-10-14 기준. 원본 기록(MONITOR 18GB 등)은 수치를 이 문서에 옮긴 뒤 삭제했다. `lab/twenty/record.sh`로 다시 만들 수 있다.)

## 5. 다음 작업: Twenty race 검증

Twenty 엔티티 캐시의 미스 경로(`recomputeFromProvider`)는 DB를 읽은 뒤 `MSET`으로 `:hash`(랜덤 UUID)와 `:data`를 **조건 없이** 덮어쓴다. 리스나 버전 비교가 없다. `:hash`는 로컬 캐시 갱신용 표식이지 DB 버전이 아니다. 따라서 교과서적인 stale-set 경쟁이 가능한 구조다.

현실적인 상황으로 설계한다. 관리자가 워크스페이스 설정(이름, 메타데이터)을 바꾸는 동안, 다른 사용자들의 모든 인증 요청이 workspace 캐시를 읽는 상황이다. 억지 부하로 만든 경쟁은 버그로 인정받기 어렵기 때문이다 (PLAN 15장).

### 5.1 실험 구성 (`lab/twenty/race.sh`, `race.js`, `race_analyze.py`)

- 시드된 Twenty 테스트 DB 위에 Twenty 서버를 1대 또는 2대 띄운다. 운영의 수평 확장을 흉내 낸다.
- **리더 50개**가 관리자 토큰으로 `currentWorkspace`를 계속 요청한다. 모든 인증 요청이 JWT 전략에서 workspace 엔티티 캐시를 읽으므로, 무효화 직후의 재충전은 리더가 만든다.
- **쓰기**는 워크스페이스 이름을 `race-<n>`으로 바꾼다. 값마다 번호가 고유해서 캐시 값이 몇 번째 버전인지 바로 알 수 있다.
- **모든 실험은 외부 경로가 없는 docker 내부 네트워크 안에서만 돌린다** (`lab/twenty/compose.yaml`, `isolation.sh`). 스크립트는 기본 라우트가 보이면 실행을 거부한다.

### 5.2 측정 함정: 타임스탬프 기반 판정은 가짜를 만든다

처음에는 "Redis의 SET 시각에 이미 더 새 버전이 커밋돼 있었는가"를 타임스탬프로 판정했다. 서버 1대·쓰기 1개 실행에서 옛 값 SET이 9~60건 나왔다. 그런데 **이 판정은 전부 시계 이동 근처였고**(30초 실행마다 약 −2.9초 이동이 2회), 시계를 쓰지 않는 판정으로 다시 보니 0건이었다.

그래서 **시계를 쓰지 않는 판정**으로 바꿨다. 판정 규칙은 근거에 따라 두 종류다. **cawit으로 옮길 수 있는 것은 앞의 것뿐이다.**

| 규칙 | 근거 | 성립 조건 | cawit 일반 규칙으로 |
|---|---|---|---|
| **버전 역행**: Redis 실행 순서에서 값 v2가 SET된 뒤에 v1이 SET됨 (v1이 v2보다 먼저 커밋) | **값 기반 인과.** v2가 Redis에 들어갔다면 누군가 DB에서 v2를 읽었고, PostgreSQL에는 dirty read가 없으므로 v2는 이미 커밋된 상태다. 그 뒤의 v1 SET은 낡은 값이다 | ① v2가 WAL에 **커밋된 값으로 확인**될 것. write-through 앱이 트랜잭션 안에서 SET한 뒤 롤백하면 v2는 커밋되지 않는다 ② 같은 내용이 다시 나타나지 않을 것(ABA). 버전 컬럼이나 LSN으로 구분해야 한다 | **가능** |
| **DEL 이후 옛 값**: i번째 DEL 뒤에, 커밋 순서상 앞쪽 i개 중 마지막이 아닌 값을 SET | **앱 지식 기반 인과.** "Twenty는 커밋한 뒤 DEL한다", "이 실험에서는 DEL 수 = 쓰기 수 = 커밋 수" | Twenty와 이 실험에서만 | **불가** |

분석기는 역행 판정에서 WAL에 커밋으로 나온 값만 쓰고, 실험 값은 `race-<n>`으로 고유해서 ABA도 생기지 않는다. 역행 규칙은 Redis에 새 값이 먼저 SET된 경우만 잡는다. DEL로만 무효화하는 앱에서는 새 값이 재충전으로만 들어오므로 적용 범위가 좁다. 아래 표에서 두 규칙의 건수가 다른 이유다.

**설계에 주는 의미 (PLAN 9.5·9.6)**: 판정은 가능한 한 **순서**로 해야 한다. Redis 쪽 순서는 keyspace 알림과 MONITOR가 실행 순서 그대로 준다. DB 쪽 순서는 WAL이 준다. 두 시스템 사이를 잇는 일반 규칙은 값 기반 인과(Redis에 들어간 값은 이미 커밋됐다)다. "커밋 다음에 무효화"는 앱마다 다르므로 일반 규칙으로 쓰지 않는다. 타임스탬프는 지속 시간을 잴 때만 쓰고, 시계 이동이 끼면 그 값은 믿지 않는다.

- **관리자 한 명이 순서대로 고치는 경우에는 경쟁이 생기지 않았다**(1,824회 중 0, 95% 상한 0.21%). 재충전은 DEL 직후 1ms 안에 시작해 약 2ms 만에 끝나는데, 다음 rename은 요청 처리에 수십 ms가 걸려서 그 구간에 들어오지 못한다. 서버 프로세스 하나 안에서는 동시 미스도 메모이저로 하나로 합쳐진다.
- **같은 워크스페이스를 동시에 계속 고치면 stale-set 경쟁이 실제로 생긴다.** 버전 역행만으로도(앱 지식 없이) 4·16·9·28건이 나왔다. Twenty의 재충전 경로(`recomputeFromProvider`)가 버전 비교 없이 `MSET`으로 덮어쓰기 때문이다.
- **같은 조건을 다시 돌리면 결과가 2.7배까지 달랐다**(0.93%와 0.35%). 낡은 값 쓰기는 시간적으로 몰려서 생기므로, 쓰기마다 독립이라고 가정한 신뢰구간은 실제 불확실성을 과소평가한다. 실행 한 번끼리의 비교는 약한 근거다.
- **DB 지연은 차이를 감지하지 못했다**(0.93% 대 1.12%, 두 비율 검정 z ≈ 0.76. 위의 실행 간 변동을 생각하면 근거는 더 약하다). 이론상으로는 오히려 줄어야 했다. 라이터는 커밋한 뒤 조회를 한 번 더 하고 나서 DEL하므로, DB 왕복이 늘면 DEL 쪽이 왕복 한 번만큼 더 밀리기 때문이다. 예측과 측정이 맞지 않은 이유는 아직 모른다. 어느 쪽이든 **DB 지연은 경쟁을 키우는 수단이 아니고, 키우려면 리더 쪽(재충전)만 늦춰야 한다.**
- **허용치 기준으로 보면 위반은 0건이다.** Twenty는 명시된 신선도 정책이 없으므로, 로컬 캐시 확인 주기(`LOCAL_TTL_MS = 100`)를 **설계상 허용치로 추정**해 `max_staleness = 100ms`로 둔다. 쓰기 8개 동시 실행은 "경쟁 33건, Redis까지 온 낡은 읽기 30회, **허용치 위반 0건**"이다. 낡은 값은 최대 43ms만 남았다. "피해 없음"이 주관적 판단이 아니라 PLAN의 판정 모델(사실 → 정책)로 나온 결과다.
- **몰아치기 약 1,114회에서는 끝난 뒤 낡은 값이 남은 경우가 한 번도 없었다**(Wilson 95% 상한 0.34%). 사용자 피해는 낡은 값이 "마지막 쓰기"가 될 때 생기므로, 피해 확률을 보여주는 것은 연속 쓰기가 아니라 이쪽이다.

### 5.4 해석

**Twenty 한 곳의 결과로 보면, stale-set 경쟁은 코드에 실제로 있고 관측으로 확정할 수 있지만, 지금 구조에서는 허용치를 넘는 피해로 이어지지 않는다.** 재충전 경로가 짧기 때문이다(DB를 한 번 읽고 곧바로 `MSET`). 0단계 실험에서 끝까지 남는 낡은 값이 나온 것은, DB 읽기와 캐시 쓰기 사이에 0~5ms의 처리 시간을 두었기 때문이다.

**일반화의 한계**: 실제 앱은 Twenty 하나다. check 모드와 race 모드의 결과는 같은 앱에서 나왔으므로 독립된 표본 두 개가 아니다. Twenty는 재충전 경로가 짧고 무효화 호출이 한곳에 모여 있는 앱이다. 이 결과는 "잘 만든 앱에서는 무해했다"까지만 말하고, "다른 앱에서도 무해하다"나 "허술한 앱에서는 피해가 난다"는 말하지 않는다.

**프로젝트의 핵심 가설에 주는 의미**

- 가설은 **조건부로만** 성립한다. 낡은 값이 남을 확률은 "DB 읽기와 캐시 쓰기 사이의 간격"과 "같은 행에 대한 동시 쓰기 빈도"에 달려 있다.
- 그래서 **race 모드의 증폭기가 핵심**이다. 이런 잠재적 경쟁은 우연에 맡기면 CI에서 드러나지 않는다. 다만 "지연을 넣었더니 낡은 값이 남았다(예/아니오)"는 메인테이너에게 인위적인 조건으로 들린다. 결과를 **"재충전 지연이 X ms일 때 낡은 값이 남을 확률이 Y%"** 형태로 정량화해야 한다(5.6).
- 외부 검토는 제품 정의를 "버그 탐지"에서 **"위험 정량화 + 수정 검증"**으로 옮기는 것을 제안했다. 수정 검증은 버전 비교 SET이나 lease를 넣은 뒤 같은 조건에서 확률이 0이 됐음을 CI에서 증명하는 것이다. 방향은 이 데이터와 맞지만, 실제 앱 하나의 결과이므로 제품 정의 결정은 보류한다.
- 홍보 메시지: "교과서 패턴은 낡은 값을 남긴다"가 아니라, **"버전 비교 없이 덮어쓰는 캐시는 재충전이 느려지는 순간 낡은 값을 남길 수 있다. 그 조건을 CI에서 재현하고 확률로 보여준다."**

### 5.5 조작 확인 (manipulation check)

증폭기를 붙인 첫 실행은 **무효였다.** Twenty의 `.env.test`가 프로세스 환경 변수보다 우선 적용돼서, 서버가 프록시가 아닌 Redis에 직접 붙었다. 프록시 통계는 `conns:1, commands:0`이었고 그 결과는 사실상 증폭 없는 재실행(위 표의 0.35%)이다. 같은 원인으로 설정이 무시된 것이 두 번째였다.

그래서 지연을 거는 모든 실행에 **조작 확인**을 자동으로 넣었다 (`race.sh`).

- **증폭기**: 프록시가 늦춘 명령 수가 0보다 크고, MONITOR에 기록된 workspace `:data`의 SET·MSET 수와 **정확히 같아야** 한다. 같으면 모든 재충전 쓰기가 프록시를 거쳤다는 뜻이다. (같은 네트워크 공간이라 `CLIENT LIST`의 접속 주소로는 직접 접속과 프록시 경유를 구분할 수 없다.)
- **코드 지연**: 서버들이 로그로 남긴 지연 적용 횟수의 합이 같은 SET·MSET 수와 정확히 같아야 한다.
- 하나라도 틀리면 그 실행을 실패로 처리하고 결과를 쓰지 않는다.

**설계에 주는 의미 (PLAN 9.9)**: cawit의 race 모드도 같은 장치가 필요하다. 주입한 교란이 실제로 대상 명령에 걸렸는지 스스로 확인하고, 아니면 결과를 `INCONCLUSIVE`로 낸다.

### 5.6 재충전 지연-확률 곡선

**질문**: 재충전이 느려지면, 몰아치기가 끝난 뒤 낡은 값이 남을 확률은 얼마인가? 앱 코드를 고치지 않는 증폭기는 실제 느린 재충전을 얼마나 흉내 내는가?

**두 가지 방법으로 같은 지연을 건다.**

- **코드 지연 (기준선)**: Twenty 소스의 재충전 경로, DB 읽기와 `MSET` 사이에 테스트 전용 지연을 넣었다 (`lab/twenty/refill-delay.patch`, `CW_REFILL_DELAY_MS`). 실제로 느린 재충전이다. 그 요청만 늦어지고 Redis 연결은 막히지 않는다.
- **증폭기**: 프록시가 workspace `:data`의 SET·MSET만 늦춘다 (`lab/twenty/amp-proxy.js`). Twenty는 프로세스마다 캐시용 Redis 연결이 하나라서, 늦춘 MSET 뒤에 **같은 서버의 DEL·GET·MGET도 막힌다**(head-of-line blocking). 그러면 같은 서버 안에서 생긴 낡은 값은 뒤따르는 DEL에 지워진다. 그래서 증폭기는 사실상 **서버 간 경쟁만** 잰다. 이것은 연결 단위 증폭기의 구조적 한계다.

**조건**: 서버 2대, 리더 50개, 동시 rename 8개로 몰아치기 → 600ms 쉼, 지점마다 360초(몰아치기 약 300회). 결과는 몰아치기 단위로 시계 없이 판정한다. k번째 DEL 이후 다음 몰아치기 전까지 마지막으로 SET된 값이 그 몰아치기의 마지막 커밋 값보다 오래됐으면 "남음"이다. Wilson 95% 구간과 남은 시간, 허용치(100ms) 위반 수를 함께 기록한다.

**일정한 지연에서는 남지 않았다.** 20ms 고정 지연에서 코드 지연 98회, 증폭기 97회 모두 0건이었다(조작 확인 통과: 지연 적용 595·606회가 재충전 SET 수와 일치). 지연이 일정하면 먼저 DB를 읽은 재충전이 먼저 쓴다. 그래서 몰아치기의 마지막 DEL 뒤에 시작한 새 재충전이 항상 마지막에 써진다. 낡은 값이 남으려면 **먼저 읽은 재충전이 나중에 읽은 재충전보다 늦게 써야** 한다. 즉 지연이 들쭉날쭉해야 한다. 실제 운영에서 문제가 되는 것도 이 경우다(요청 하나가 GC 정지나 느린 쿼리로 늦어지는 경우). 그래서 곡선은 **0~N ms 사이 무작위 지연**으로 잰다. 이 점에서 두 방법의 차이가 예상된다. 증폭기는 연결 하나 안에서 순서를 지키므로, 무작위 지연을 줘도 같은 서버 안에서는 쓰기 순서가 뒤집히지 않는다.

**결과** (조작 확인은 모든 지점 통과: 지연 적용 횟수 = 재충전 SET 수)

| 지연 (무작위 0~N ms) | 코드 지연: 남음 / 몰아치기 | 확률 (Wilson 95%) | 증폭기: 남음 / 몰아치기 | 확률 (Wilson 95%) |
|---|---|---|---|---|
| 5 | 0 / 573 | 0% (< 0.67%) | 0 / 589 | 0% (< 0.65%) |
| 20 | 1 / 571 | 0.18% (0.03–0.98%) | 0 / 588 | 0% (< 0.65%) |
| 35 | — | — | 63 / 576 | 10.9% (8.6–13.8%) |
| 50 | 4 / 587 | 0.68% (0.27–1.74%) | 101 / 572, 재실행 132 / 572 | 17.7% (14.8–21.0%), 23.1% (19.8–26.7%) |
| 70 | — | — | 42 / 576 | 7.3% (5.4–9.7%) |
| 100 | 7 / 587 | 1.19% (0.58–2.44%) | 8 / 576 | 1.4% (0.7–2.7%) |

- **실제 느린 재충전(코드 지연)에서는 확률이 지연에 따라 단조롭게 오른다.** 남은 낡은 값은 모두 다음 몰아치기까지(약 600ms) 유지됐다. 실제 운영이라면 다음 수정이나 TTL(Twenty 엔티티 캐시는 7일)까지 남는다. 허용치(100ms) 위반은 남은 경우와 같은 수다.
- **증폭기는 실제를 흉내 내지 못한다.** 곡선이 50ms 근처에서 정점을 찍는 산 모양이고, 35~70ms에서 실제보다 10~30배 높다. 100ms에서 비슷해진 것은 우연으로 보인다. 50ms를 다시 돌려도 높게 나와 재현된다.
- **원인은 연결 단위 대기열(head-of-line blocking)이다.** 프록시가 기록한 바로는, 실행마다 명령 약 5만 개가 늦춘 명령 뒤에서 기다렸고, 대기 시간 합계가 700~1,500초, 최대 대기가 128~258ms였다. Twenty는 프로세스마다 캐시용 Redis 연결 하나를 공유하므로, MSET 하나를 늦추면 그 서버의 로컬 캐시 확인(`GET :hash`), MGET, DEL이 모두 뒤로 밀린다. 그 결과는 재충전 지연이 아니라 대기열의 동역학에 좌우된다. 정점이 왜 50ms 근처인지는 아직 설명하지 못했다.

**이 곡선이 말하는 것과 말하지 않는 것**

- 말하는 것: Twenty에서, 같은 워크스페이스에 동시 수정 8개가 몰리고 재충전이 0~N ms 무작위로 느려지면, 몰아치기 1회당 낡은 값이 남을 확률은 N=20에서 약 0.2%, 50에서 약 0.7%, 100에서 약 1.2%다.
- 말하지 않는 것: 실제 재충전 지연은 균등분포가 아니라 꼬리가 긴 분포다. 0~100ms 균등분포는 평균 50ms로, 평상시보다 훨씬 느린 상태를 가정한다. 동시 수정 8개도 Twenty의 일상적인 사용 패턴이 아니다. 각 지점은 실행 한 번이고, 같은 조건에서도 실행 간 변동이 있다(5.3).

**설계에 주는 의미 (PLAN 9.9)**

- **연결 단위 프록시 증폭기는 멀티플렉싱 클라이언트에서 위험을 크게 부풀린다.** 이 방식으로 낸 확률을 사용자에게 "위험"으로 보여주면 안 된다. 외부 검토가 지적한 "인위적인 조건" 비판에 정확히 해당한다.
- **현실적인 증폭은 앱 안에서 재충전 경로만 늦추는 것이다.** 이번의 코드 지연이 그 방식이다. cawit에서는 instrumented 모드(계측 훅이나 SDK)로 재충전 경로에 지연을 주입하는 쪽이 맞다.
- 프록시 증폭기를 남긴다면 대안이 있다. 늦출 명령만 붙잡고, 키가 겹치지 않는 뒤 명령은 먼저 실행한 뒤 응답 순서만 맞춰 돌려주는 방식이다. Redis 쪽 대기열은 없어지지만, 같은 연결을 쓰는 다른 요청이 응답을 늦게 받는 문제는 남는다. 커넥션 풀(요청마다 다른 연결)을 쓰는 클라이언트에서는 지금 방식도 왜곡이 작을 수 있지만 측정하지 않았다.
- **두 곡선을 비교한 것 자체가 race 모드의 검증 절차가 된다.** 증폭 방식을 바꿀 때마다 앱 내부 지연 기준선과 겹치는지 확인해야 한다.

### 5.7 3라운드: 기준선 종류, 평균을 맞춘 비교, 반복, 현실 조건

외부 검토에서 받은 질문 네 가지를 쟀다. 조건은 5.6과 같다(서버 2대, 리더 50개, 동시 rename 8개 몰아치기 → 600ms 쉼, 지점마다 360초). 모든 실행이 조작 확인을 통과했다.

**① 기준선 종류: 프로세스 정지형 지연도 증폭기와 다르다**

| 재충전 지연 (무작위 0~N) | 요청 단위 지연 (`await sleep`) | 프로세스 정지 (바쁜 대기) | 증폭기 |
|---|---|---|---|
| 50ms | 5 / 1,172 = 0.43% (0.18–1.00%), 2회 합산 | 5 / 573 = 0.87% (0.37–2.03%) | 101 / 572, 132 / 572 = 17.7%, 23.1% |
| 100ms | 11 / 1,165 = 0.94% (0.53–1.68%), 2회 합산 | 6 / 571 = 1.05% (0.48–2.27%) | 8 / 576 = 1.4% |

프로세스 전체를 멈추는 지연(GC 정지, 이벤트 루프 블로킹 흉내)도 요청 단위 지연과 비슷한 수준이다. **증폭기는 둘 중 어느 쪽도 흉내 내지 못한다** (50ms에서 20배 이상). 검토가 제기한 "증폭기는 프로세스 정지형에 가까울 수 있다"는 가능성은 이 측정으로 배제된다.

**② "위험은 지연의 편차에서 나온다"는 가설: 지지되지 않는다**

| 평균 지연 | 일정한 지연 | 무작위 지연 (0~2×평균) |
|---|---|---|
| 20ms | 40ms: 2 / 584 = 0.34% | — |
| 25ms | 1 / 586 = 0.17% | 0~50ms: 5 / 1,172 = 0.43% |
| 30ms | 60ms: 2 / 583 = 0.34% | — |
| 50ms | **1회차 37 / 570 = 6.5%, 2회차 1 / 585 = 0.17%** | 0~100ms: 11 / 1,165 = 0.94% |
| 100ms (일정) | 1 / 579 = 0.17% | — |

- 일정한 지연에서도 낡은 값은 남는다(대부분 0.2~0.3%). 5.6의 "일정 20ms에서 0건"은 몰아치기 98회뿐이라 생긴 착시였다.
- 무작위 지연이 일정한 지연보다 다소 높게 나오지만, 실행 간 변동(아래 ③)을 생각하면 차이를 주장할 근거가 없다.

**③ 실행마다 다른 "체제"에 들어간다**

일정 50ms 1회차는 6.5%였고, 낡은 값이 실행 **내내 고르게** 나왔다(6구간 각각 4~11건). 같은 조건의 2회차는 0.17%(6구간 중 한 곳에서 1건)였다. 실행이 시작될 때 들어간 상태가 6분 동안 유지된 것이다.

1회차의 메커니즘은 MONITOR로 확인했다(쓰기가 자기가 무효화하는 캐시를 인증에 쓰는 되먹임).
1. 서버 A가 rename 4개를 커밋하고 DEL한다.
2. A의 리더들이 재충전을 시작해 DB에서 값을 읽고 50ms 기다린다.
3. 서버 B가 맡은 rename 4개는 **인증 단계에서 같은 workspace 캐시를 읽어야 해서** B 쪽 재충전(역시 50ms)을 기다린다.
4. 그래서 B의 커밋이 A의 재충전이 끝나기 직전에 몰리고, A가 옛 값을 MSET한다.
5. B는 그 값을 그대로 가져다 쓰고, 낡은 값이 다음 몰아치기까지 남는다.

같은 메커니즘이 2회차에서는 거의 작동하지 않았는데, 그 이유는 아직 모른다.

**의미**: 실행 하나 안의 몰아치기 수백 회로 계산한 Wilson 구간은 실제 불확실성을 크게 과소평가한다. 위험 수치는 **독립된 실행 여러 번(재시작 포함)의 분포**로 내야 하고, 실행 간 퍼짐을 함께 보고해야 한다. 증폭기 50ms의 높은 값은 두 실행 모두에서 나왔으므로 이 체제 문제와는 별개다.

**④ 지연이 클수록 높아지는가 (요청 단위 지연, 반복 합산)**

5ms 0 / 573, 20ms 1 / 571, 50ms 5 / 1,172, 100ms 11 / 1,165. 양 끝(5ms 대 100ms)은 Fisher 정확 검정 p ≈ 0.02로 차이가 있다. 중간 지점들은 구간이 겹친다. 그래서 **"지연이 크면 높아지는 경향이 있다"까지만 말할 수 있고, 곡선의 모양은 주장하지 않는다.** ③을 생각하면 이 판단도 실행 수가 늘면 바뀔 수 있다.

**⑤ 현실 조건: 낡은 값이 남지 않았다**

한 사람이 1~3초 간격으로 저장하고(무작위), 리더 50개가 같은 워크스페이스를 계속 쓰고, 재충전이 0~100ms 무작위로 느린 조건에서 15분 동안 **저장 477회 중 0건**이었다(95% 상한 0.80%). 저장 사이의 간격(초 단위)이 재충전 지연(100ms 이하)보다 훨씬 길어서, 경쟁 구간이 겹칠 기회가 없다.

**→ Twenty에 버그로 보고할 근거는 없다.** stale-set 경쟁은 코드에 있지만, 현실적인 사용 패턴에서는 낡은 값이 남지 않았다. 같은 워크스페이스를 동시에 여럿이 고치는 경우에만 드물게 남는다.

**3라운드에서 바뀐 결론**

| 이전 판단 | 지금 |
|---|---|
| 일정한 지연에서는 낡은 값이 남지 않는다 | **철회.** 표본이 작아서 생긴 착시였다 |
| 위험은 지연의 편차에서 나온다 (가설) | **지지되지 않음** |
| 실제 느린 재충전에서 확률이 단조롭게 오른다 | 경향만 있다 (양 끝 p ≈ 0.02) |
| 증폭기는 실제를 흉내 내지 못한다 (요청 단위 기준선 대비) | **범위 확장**: 프로세스 정지형 기준선과도 다르다 |
| (새로) | 실행마다 다른 체제에 들어갈 수 있다. 위험 수치는 여러 번의 독립 실행으로 내야 한다 |
| (새로) | 현실 조건(한 사람의 저장)에서는 0 / 477 |

**측정 함정 (3라운드)**

- DB 초기화가 "성공"을 보고했는데 그 안의 시드 명령은 실패해, 모든 요청이 `Workspace not found`로 끝났다. 조작 확인(지연 적용 0회)이 잡아냈다. 지금은 초기화 뒤에 시드된 워크스페이스를 직접 확인한다.
- 조작 확인을 "정확히 일치"로 걸었더니, MONITOR가 시작되기 전의 재충전 5회(0.15%) 때문에 정상 실행이 실패로 처리됐다. 게다가 실패 처리가 WAL 수집보다 먼저 일어나서 그 실행을 분석할 수 없었다. 지금은 WAL을 먼저 모으고, 기준을 "지연 적용 ≥ 관측된 재충전, 초과는 0.5% + 5 이내"로 바꿨다.

### 5.8 결정적 재현과 수정 검증 (동기화 지점)

확률 방식은 실행마다 결과가 갈려서, 수정 전에도 0건이 나올 수 있었다(양성 대조 불안정). 그래서 순서를 강제하는 **동기화 지점**으로 같은 경쟁을 매번 재현하고, 수정 후보를 검증했다 (당시 `lab/twenty/sync.sh`, `sync-scenario.js`, `refill-delay.patch`의 `CW_SYNC`·`CW_FIX`. 2단계에서 `cawit verify`와 `lab/twenty/verify.sh`로 대체했고 원본은 git 기록에 있다).

**한 회차의 순서**
1. 서버 A에 rename → A가 커밋하고 무효화한다. A의 메모이저도 비워진다.
2. 동기화 지점을 장전하고 A에 읽기를 보낸다 → A가 미스로 DB를 읽은 직후(옛 값) 멈추고 신호를 보낸다.
3. 서버 B에 rename → B가 새 값을 커밋하고 무효화한다.
4. A를 풀어 준다 → A가 읽어 둔 값을 쓴다.
5. Redis와 DB를 비교한다.
6. A에 한 번 더 읽고, 캐시가 새 값으로 다시 채워지는지 본다(수정이 캐시를 아예 막지는 않는지).

"신호를 보냈다"(2단계)가 조작 확인이다. 모든 회차에서 도달했다.

| 버전 | 낡은 값 (5단계) | 다시 채워짐 (6단계) | 판정 |
|---|---|---|---|
| 수정 전 (조건 없는 `MSET`) | **20 / 20** | — | 매번 재현된다 |
| 버전 비교 SET (`updatedAt`이 더 최신일 때만 씀, Lua) | **20 / 20** | — | **그럴듯하지만 고치지 못한다.** DEL 뒤에는 비교할 값이 없다 |
| 리스 (읽기 전에 리스, 무효화가 리스를 지움, 리스가 남아 있을 때만 씀) | 0 / 20 (비어 있음) | **0 / 20** | Redis는 깨끗하지만 **불완전하다.** 거부된 값을 그대로 돌려주면 Twenty의 메모이저가 그 옛 값을 서버 안에서 10초 동안 응답한다 |
| 리스 + 거부되면 DB 다시 읽기 (최대 3회) | **0 / 20** (20회 최신) | **20 / 20** | **고친다** |

**의미**

- 결정적 방식은 수정 전 100% 실패, 올바른 수정 100% 통과로 **양성 대조가 매번 확실하다.** 한 번에 1분 남짓이고 결과가 흔들리지 않으므로 CI에 넣을 수 있다.
- 더 중요한 것은 **그럴듯한 수정 두 개를 걸러냈다**는 점이다. 버전 비교 SET은 아예 효과가 없었고, 리스만 넣은 버전은 Redis에서는 깨끗해 보였지만 프로세스 안 메모이저로 옛 값을 10초 동안 응답했다. 확률 방식이나 Redis 상태만 보는 검사로는 둘 다 통과로 보였을 것이다.
- 비용: Twenty의 재충전 경로 한 곳에 훅을 넣었다(읽은 직후 동기화 지점). 앱 코드 수정이 필요하다는 점은 PLAN 0장의 현재 상태 그대로다.
- **재현성 확인 (2026-10-16)**: 재부팅으로 체크아웃이 사라져 `lab/twenty/setup.sh`로 같은 커밋을 새로 받아 다시 빌드했다. 네 버전 모두 같은 결과가 나왔다(20/20, 20/20, 0/20·재충전 0/20, 0/20·재충전 20/20).
- 이 결과가 외부 검토가 제안한 제품 정의("캐시 동시성 버그를 순서까지 통제해 재현하고, 고친 뒤 고쳐졌음을 증명하는 테스트 도구")의 첫 실증이다. **2026-10-16에 이 정의로 바꿨다** (PLAN 0장).
