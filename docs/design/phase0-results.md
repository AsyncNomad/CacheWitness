# 0단계 결과 기록

0단계의 목표는 프로토타입의 판정이 독립적인 정답과 얼마나 맞는지 재는 것이다 (PLAN 13장). 이 문서는 실행할 때마다 결과를 덧붙이는 기록이다.

## 실험 환경

| 항목 | 값 |
|---|---|
| 호스트 | WSL2 Ubuntu 24.04, 24코어, 15GB RAM (프로토타입 원래 검증: 2코어, 7GB) |
| DB | `postgres:16`, `wal_level=logical`, `users(id, name, version)` 5,000행, `REPLICA IDENTITY FULL` |
| 캐시 | `redis:7.2`, DEL·UNLINK 권한이 없는 ACL 사용자 `noinv` |
| 클라이언트 | node-redis 6.3.0, pg 8.23.1 (Node 22 컨테이너, host 네트워크) |
| 프로토타입 | `spikes/prototype/` 원본 그대로, 유예 시간 300ms, test_decoding 폴링 |

재현 방법:

```bash
docker compose -f lab/compose.yaml up -d --wait
(cd spikes/prototype/cachewitness && cargo build --release)
docker run --rm -u "$(id -u):$(id -g)" -e npm_config_cache=/tmp/.npm \
  -v "$PWD/spikes/prototype/harness":/h -w /h node:22-slim npm ci
lab/repro.sh injected     # 주입 버그 400건 + 백그라운드 부하
lab/repro.sh natural      # 버그 없는 cache-aside, 핫키 200개, 워커 32개, 20초
```

결과는 `lab/out/<모드>-<시각>/`에 남는다 (git에는 넣지 않는다).

## 2. 발견: 원인 판정 오류의 실제 사례

### 2.1 교차 연결 순서 역전으로 원인을 잘못 확정 (user:2139)

버그가 없는 실행인데 `INVALIDATE_BEFORE_COMMIT`으로 판정됐다. `natural.js`는 항상 커밋한 다음에 DEL하므로 이 판정은 틀렸다.

```
 -6.6ms  conn 6  DEL                ← 이전 쓰기(v617)의 무효화
 -1.6ms  conn 1  GET miss
  0.0ms  DB      COMMIT v619
 +0.8ms  conn 1  SET v618           ← 프록시 기록상 DEL보다 먼저
 +1.0ms  conn 3  DEL                ← 이번 쓰기의 무효화
 검사: 캐시 = v618
```

캐시에 v618이 남았으므로 Redis의 실제 실행 순서는 DEL → SET이었다. 그런데 프록시는 클라이언트에서 요청 바이트를 읽은 시각 하나만 기록한다. 그래서 서로 다른 연결의 두 명령이 **0.2ms 차이로 뒤집혀** 기록됐다. 규칙은 "커밋 후 DEL이 SET보다 앞섬"을 찾지 못했고, 1초 창 안에 있던 **이전 쓰기의 DEL**을 끌어와 커밋 전 무효화로 확정했다.

**의미**: 이벤트마다 시각 하나만 두면 원인을 잘못 확정한다는 것이 실제로 확인됐다. 시간 구간 모델로 기록했다면 SET과 DEL의 구간이 겹쳐 `ORDER_UNCERTAIN`이 됐을 것이다 (PLAN 9.5). `ibc_window`(1초)도 쓰기가 잦은 키에서 이전 쓰기의 DEL을 끌어온다.

### 2.2 경쟁 간격은 대부분 1ms 미만

`STALE_SET_RACE` 7건에서 DEL과 옛 값 SET 사이 간격(프록시 기록 기준):

| 키 | DEL | 옛 값 SET | 간격 | 리더의 GET miss | 낡은 값을 돌려준 GET 히트 |
|---|---|---|---|---|---|
| user:2034 | +1.5ms | +2.3ms | 0.8ms | -0.4ms | 15 |
| user:2179 | +1.9ms | +2.3ms | 0.4ms | **+0.6ms** | 4 |
| user:2079 | +1.8ms | +2.1ms | 0.3ms | -2.0ms | 4 |
| user:2107 | +1.6ms | +4.8ms | 3.2ms | **+0.3ms** | 1 |
| user:2022 | +1.5ms | +2.4ms | 0.9ms | -1.2ms | 1 |
| user:2106 | +1.3ms | +4.5ms | 3.2ms | -0.4ms | 0 |
| user:2111 | +1.4ms | +2.3ms | 0.9ms | **+0.2ms** | 0 |

- 7건 중 5건이 1ms 미만이다. PLAN의 "실제 경쟁 간격 약 7ms"는 느린 환경의 값이었다. 빠른 환경일수록 순서 판정이 시계·관측 오차에 더 민감하다.
- **3건은 리더의 GET miss가 커밋 이후**인데, 보고서 문구는 "커밋 전에 DB를 읽었다"고 쓴다. 레플리카가 없는 환경이므로 두 가지 설명이 가능하다.
  1. 멀티플렉싱: `natural.js`는 워커 4개가 연결 하나를 공유한다. 같은 연결의 **다른 워커**가 낸 미스를 리더의 미스로 잘못 연결했다.
  2. 커밋 시각과 가시성의 차이: WAL의 커밋 시각은 다른 세션에 보이기 전에 찍힌다. 커밋 시각 직후에 시작한 SELECT가 아직 옛 버전을 볼 수 있다 (PLAN 17장 사각지대).

  둘을 가리려면 앱 쪽의 정답(요청 ID, SELECT 시각, 읽은 버전)이 필요하다. 다음 작업인 정답 하네스가 이것을 기록한다.
- 위반 키의 절반 이상에서 낡은 값이 실제로 읽혔다. "낡은 읽기 제공 횟수"를 1급 지표로 두기로 한 결정(PLAN 3.1)을 뒷받침한다.

### 2.3 보고서 문구의 버전 번호가 실제 버전이 아니다

설명문의 `v63`, `v62`는 키별 버전 링 버퍼(최대 64개)의 인덱스다. 실제 DB 버전(582, 581)과 다르다. 사람이 읽는 보고서에서 혼동을 일으킨다. 새 구현에서는 DB 쪽 식별자(LSN 또는 사용자가 지정한 버전 컬럼)를 쓴다.

## 3. 다음 작업

1. **정답 하네스**: 앱 쪽에서 요청 ID, 연결 번호, GET·SELECT·SET·UPDATE·DEL 각각의 시작·끝 시각, 읽은 버전, 읽기 대상을 JSONL로 기록한다. 이 기록으로 위반마다 "실제 원인"을 정한다. OpenTelemetry 자동 계측을 함께 켜서, span만으로 같은 정답을 복원할 수 있는지도 잰다.
2. **실험 행렬**: 클라이언트 연결 구성(공유 연결 / 워커별 연결) × 읽기:쓰기 비율(2.3:1, 20:1, 100:1) × 레플리카 유무(`recovery_min_apply_delay`로 지연 고정).
3. **confusion matrix**: 프로토타입 판정과 정답 원인을 키별로 비교한다. 특히 "잘못된 확정"의 비율을 잰다.
