## 2. 발견: 원인 판정 오류의 실제 사례

### 2.1 교차 연결 순서 역전으로 원인을 잘못 확정 (user:2139)

버그가 없는 실행인데 `INVALIDATE_BEFORE_COMMIT`으로 판정됐다. `natural.js`는 항상 커밋한 다음에 DEL하므로 이 판정은 틀렸다.

```
 -6.6ms  conn 6  DEL                ← 이전 쓰기(v617)의 무효화
 -1.6ms  conn 1  GET miss
  0.0ms  DB      COMMIT v619
 +0.8ms  conn 1  SET v618           ← 프록시 기록상 DEL보다 먼저
 +1.0ms  conn 3  DEL                ← 이번 쓰기의 무효화
 검사: 캐시 = v618
```

캐시에 v618이 남았으므로 Redis의 실제 실행 순서는 DEL → SET이었다. 그런데 프록시는 클라이언트에서 요청 바이트를 읽은 시각 하나만 기록한다. 그래서 서로 다른 연결의 두 명령이 **0.2ms 차이로 뒤집혀** 기록됐다. 규칙은 "커밋 후 DEL이 SET보다 앞섬"을 찾지 못했고, 1초 창 안에 있던 **이전 쓰기의 DEL**을 끌어와 커밋 전 무효화로 확정했다.

**의미**: 이벤트마다 시각 하나만 두면 원인을 잘못 확정한다는 것이 실제로 확인됐다. 시간 구간 모델로 기록했다면 SET과 DEL의 구간이 겹쳐 `ORDER_UNCERTAIN`이 됐을 것이다 (PLAN 9.5). `ibc_window`(1초)도 쓰기가 잦은 키에서 이전 쓰기의 DEL을 끌어온다.

### 2.2 경쟁 간격은 대부분 1ms 미만

`STALE_SET_RACE` 7건에서 DEL과 옛 값 SET 사이 간격(프록시 기록 기준):

| 키 | DEL | 옛 값 SET | 간격 | 리더의 GET miss | 낡은 값을 돌려준 GET 히트 |
|---|---|---|---|---|---|
| user:2034 | +1.5ms | +2.3ms | 0.8ms | -0.4ms | 15 |
| user:2179 | +1.9ms | +2.3ms | 0.4ms | **+0.6ms** | 4 |
| user:2079 | +1.8ms | +2.1ms | 0.3ms | -2.0ms | 4 |
| user:2107 | +1.6ms | +4.8ms | 3.2ms | **+0.3ms** | 1 |
| user:2022 | +1.5ms | +2.4ms | 0.9ms | -1.2ms | 1 |
| user:2106 | +1.3ms | +4.5ms | 3.2ms | -0.4ms | 0 |
| user:2111 | +1.4ms | +2.3ms | 0.9ms | **+0.2ms** | 0 |

- 7건 중 5건이 1ms 미만이다. PLAN의 "실제 경쟁 간격 약 7ms"는 느린 환경의 값이었다. 빠른 환경일수록 순서 판정이 시계·관측 오차에 더 민감하다.
- **3건은 리더의 GET miss가 커밋 이후**인데, 보고서 문구는 "커밋 전에 DB를 읽었다"고 쓴다. 레플리카가 없는 환경이므로 두 가지 설명이 가능하다.
  1. 멀티플렉싱: `natural.js`는 워커 4개가 연결 하나를 공유한다. 같은 연결의 **다른 워커**가 낸 미스를 리더의 미스로 잘못 연결했다.
  2. 커밋 시각과 가시성의 차이: WAL의 커밋 시각은 다른 세션에 보이기 전에 찍힌다. 커밋 시각 직후에 시작한 SELECT가 아직 옛 버전을 볼 수 있다 (PLAN 17장 사각지대).

  둘을 가리려면 앱 쪽의 정답(요청 ID, SELECT 시각, 읽은 버전)이 필요하다. **→ 정답 하네스로 확인한 결과 2번이다 (3.2).** 리더 미스 귀속은 맞았고, 커밋 시각 직후에 시작한 SELECT가 옛 버전을 읽었다.
- 위반 키의 절반 이상에서 낡은 값이 실제로 읽혔다. "낡은 읽기 제공 횟수"를 1급 지표로 두기로 한 결정(PLAN 3.1)을 뒷받침한다.

### 2.3 보고서 문구의 버전 번호가 실제 버전이 아니다

설명문의 `v63`, `v62`는 키별 버전 링 버퍼(최대 64개)의 인덱스다. 실제 DB 버전(582, 581)과 다르다. 사람이 읽는 보고서에서 혼동을 일으킨다. 새 구현에서는 DB 쪽 식별자(LSN 또는 사용자가 지정한 버전 컬럼)를 쓴다.

## 3. 정답 하네스 (2026-10-15)

`lab/truth/run.js`는 `natural.js`와 같은 교과서 cache-aside를 돌리면서, 앱 쪽에서 실제로 일어난 일을 기록한다.

- 요청마다 GET·SELECT·SET·UPDATE·DEL의 시작·끝 시각, 사용한 Redis 연결, 읽거나 쓴 행 버전, 읽기 대상(primary/replica)
- 쓰기마다 트랜잭션 ID. 실행 뒤 `pg_xact_commit_timestamp`로 WAL 커밋 시각을 얻는다 (`track_commit_timestamp=on`)
- 종료 시점에 Redis와 DB를 직접 비교한 결과 (오라클)

`lab/truth/analyze.py`는 이 기록과 프로토타입의 `violations.jsonl`을 맞춰 본다. 위반마다 그 값을 쓴 SET을 찾아, 같은 요청의 SELECT가 언제 어디서 읽었는지로 **실제 원인**을 정한다.

| 정답 원인 | 정의 | 프로토타입이 내야 할 답 |
|---|---|---|
| `READ_BEFORE_COMMIT` | primary에서 새 버전의 WAL 커밋 시각 전에 SELECT 시작 | `STALE_SET_RACE` |
| `READ_AFTER_COMMIT_TS` | primary에서 새 버전의 WAL 커밋 시각 **후에** SELECT를 시작했는데 옛 버전을 읽음 (3.2) | `STALE_SET_RACE` |
| `REPLICA_READ` | 지연된 레플리카에서 읽음 | `STALE_READ_AFTER_INVALIDATION` |

```bash
lab/repro.sh truth SECONDS=30 READ_RATIO=0.95 CONN_MODE=shared   # 한 번 실행
python3 -I lab/truth/analyze.py lab/out/truth-<시각>
REPEATS=3 SECS=30 lab/truth/matrix.sh                            # 실험 행렬
python3 -I lab/truth/summarize.py lab/out/matrix-<시각>.txt
docker compose -f lab/compose.yaml --profile replica up -d --wait  # 레플리카 (50ms 적용 지연)
lab/repro.sh truth SECONDS=30 READ_RATIO=0.95 REPLICA_READS=0.5
```

### 3.1 측정 함정: 벽시계가 몇십 초마다 약 2.8초 뒤로 이동한다

첫 실험 행렬에서 12회 중 8회가 "커밋 시각 → 쓰기 쪽 응답" 중앙값 약 2,800ms로 나왔다. 원인은 WSL2의 시간 동기화다. **벽시계가 수십 초마다 약 2.8초씩 한 번에 뒤로 이동하고(45초 관찰 중 −2,798ms 1회), 그 뒤 천천히 보정된다.** PostgreSQL의 커밋 시각과 프로토타입의 `SystemTime`은 벽시계를, Node의 `performance.now()`는 단조 시계를 따르므로 둘이 어긋났다.

하네스는 이렇게 고쳤다. 이벤트는 단조 시계 기준으로 기록하고, (단조 시각, 벽시계) 표본을 약 1ms마다 따로 남긴다. 분석에서 ±50ms 창의 최댓값으로 시각별 오프셋을 복원하되, 창이 이동 지점을 넘지 않게 한다. 고친 뒤에는 도구와 정답의 미스 시각 차이가 모든 위반에서 0.3ms 이내다. 첫 행렬 결과는 폐기했다.

**설계 시사점**: 운영 환경의 VM과 NTP도 벽시계를 이동시킨다. CacheWitness 자체도 이벤트는 단조 시계로 기록하고, DB 시계와의 차이를 주기적으로 다시 추정해서 이동을 감지해야 한다. 이동이 들어간 구간의 순서 판정은 `ORDER_UNCERTAIN`이다.

### 3.2 WAL 커밋 시각은 커밋이 보이는 시각이 아니다

| 지표 (18회, 레플리카 없음) | 값 |
|---|---|
| WAL 커밋 시각 → 쓰기 쪽이 커밋 응답을 받은 시각 | 중앙값 1.1~1.5ms, p99 최대 약 4.7ms |
| 새 버전의 커밋 시각 **후에** 시작했는데 옛 버전을 읽은 SELECT | 실행당 수십~수천 건, p99 0.8~6.6ms, 최대 10.9ms 늦게 시작 |
| 쓰기 쪽이 응답을 받은 **후에** 시작했는데 옛 버전을 읽은 SELECT | **0건** |

PostgreSQL은 커밋 시각을 찍은 뒤 WAL을 디스크에 쓰고 나서야 다른 세션에 커밋을 보이게 한다. 그래서 **커밋은 한 순간이 아니라 `[WAL 커밋 시각, 쓰기 쪽 응답 시각]` 구간이다.** 프록시는 쓰기 쪽 응답을 볼 수 없지만, cache-aside에서는 쓰기 쪽이 응답을 받은 다음에 DEL을 보낸다. 따라서 **커밋 이후 처음 관찰된 같은 키의 DEL이 가시성 시각의 상한**이 된다. 2.2절의 "리더의 미스가 커밋 이후" 3건도 이것으로 설명된다(정답 하네스에서 리더 미스 귀속은 모두 맞았다).

### 3.3 실험 행렬 (레플리카 없음, 30초 × 3회)

워커 32개, 핫키 200개. `shared`는 연결 8개를 워커 4개씩 공유(멀티플렉싱), `per-worker`는 워커마다 연결 1개.

| 연결 | 읽기 비율 | 쓰기/30s | 해로운 옛 값 SET (정답) | 도구가 센 옛 값 SET | 낡은 읽기 (정답) | 그중 100ms 넘음 | 종료 시 낡은 키 (탐지/오라클) | 위반 | 원인 오판정 |
|---|---|---|---|---|---|---|---|---|---|
| shared | 0.7 | 163,514 | 3,787 | 111 | 12,191 | 934 | 25/25 | 28 | 6 (21%) |
| shared | 0.95 | 59,150 | 980 | 82 | 18,544 | 7,212 | 15/15 | 173 | 23 (13%) |
| shared | 0.99 | 18,565 | 126 | 33 | 8,555 | 6,065 | 4/4 | 110 | 8 (7%) |
| per-worker | 0.7 | 149,631 | 2,824 | 119 | 10,240 | 1,027 | 14/14 | 22 | 6 (27%) |
| per-worker | 0.95 | 45,755 | 445 | 97 | 11,122 | 5,184 | 5/5 | 172 | 27 (16%) |
| per-worker | 0.99 | 11,802 | 43 | 23 | 4,003 | 3,050 | 3/3 | 72 | 5 (7%) |

(쓰기·옛 값 SET·낡은 읽기는 실행당 평균, 나머지는 3회 합계. "해로운 옛 값 SET"은 쓰기 쪽 DEL이 끝난 **뒤에** 시작해서 캐시에 남는 SET이다. DEL과 구간이 겹쳐 순서를 정할 수 없는 SET은 뺐다.)

- **낡은 상태 탐지는 완벽했다.** 종료 시점까지 남은 낡은 키 66개를 모두 탐지했다. 오라클에 없는 위반은 일시적인 낡은 상태다. 도구가 Redis를 직접 읽어 확인한 값이 새 커밋보다 오래된 버전이었으므로 실제 위반이다.
- **원인 판정은 틀린다.** 위반 577건 중 75건(13%)이 틀렸다. 버그도 레플리카도 없는 환경에서 `INVALIDATE_BEFORE_COMMIT` 43건, `STALE_READ_AFTER_INVALIDATION`(복제 지연) 32건을 단정했다. 쓰기가 잦을수록 더 틀린다(읽기 비율 0.7에서 21~27%). 이웃한 쓰기의 DEL이 1초 창 안에 들어오고, 0.2ms 단위의 순서 역전이 잦아지기 때문이다.

| 정답 \ 프로토타입 | INVALIDATE_BEFORE_COMMIT | STALE_READ_AFTER_INVALIDATION | STALE_SET_RACE |
|---|---|---|---|
| READ_AFTER_COMMIT_TS | 11 | 31 | 215 |
| READ_BEFORE_COMMIT | 32 | 1 | 287 |

- **멀티플렉싱은 원인 오판정의 주된 요인이 아니었다.** shared와 per-worker의 오판정률이 비슷하고, 리더 미스 귀속도 대부분 맞았다. 프로토타입은 이벤트를 키별로 모으므로, 같은 연결에서 다른 워커가 같은 키를 동시에 미스하는 경우가 드물다. 검토에서 우려했던 것보다 영향이 작다. 다만 이것은 이 워크로드의 결과다.
- **도구가 센 옛 값 SET은 실제의 3~50%뿐이다.** test_decoding 폴링이 늦어서, 옛 값 SET이 들어오는 순간에 도구가 아직 새 버전을 모르기 때문이다. PLAN 5.1의 "41건"도 과대가 아니라 과소 집계였다.
- **낡은 읽기는 생각보다 많다.** 읽기 비율 0.95에서 30초에 약 1만~2만 건의 GET 히트가 낡은 값을 돌려줬고, 그중 절반 가까이가 커밋 후 100ms를 넘었다. 경쟁으로 남은 낡은 값은 다음 쓰기 전까지 읽히기 때문이다.

### 3.4 레플리카 시나리오 (적용 지연 50ms, 캐시 채우기 읽기의 절반을 레플리카로)

## 4. 결론과 설계에 반영할 것

1. **사실 계층은 성립한다.** 낡은 상태 탐지는 실험 전체에서 종료 시점 낡은 키 157개를 모두 잡았다. 계획의 1계층(사실 판정)은 이 방식 그대로 갈 수 있다.
2. **원인 계층을 "확정"으로 내면 안 된다는 것이 데이터로 확인됐다.** 버그 없는 환경에서 원인의 13%를 틀리게 단정했다. PLAN 6장의 증거 모델(`UNKNOWN → SUSPECTED → CONFIRMED`)과 "배제 불가" 목록이 필요하다.
3. **커밋은 구간이다.** 시간 모델의 커밋 이벤트를 `[WAL 커밋 시각, 가시성 상한]`으로 두고, 상한은 커밋 이후 처음 관찰된 같은 키의 DEL로 좁힌다 (PLAN 9.5에 반영).
4. **시계 이동을 전제로 설계한다.** 도구는 단조 시계로 기록하고, DB 시계와의 차이를 주기적으로 추정해 이동을 감지한다 (PLAN 9.5에 반영).
5. **실제 발생률은 도구 자신의 집계로 말하지 않는다.** 폴링 지연 때문에 도구는 옛 값 SET의 대부분을 놓친다. 발생률은 정답 하네스로만 잰다 (PLAN 5.4의 원칙 유지).
